# 需求答疑闭环与标准抽离（阶段①）

## 0. 公司适配层（开工第 0 步·2026-11-13 参数化）

读 workspace `公司包/agent-company.json` 解析公司值；下文 `{paths.X}`/`{naming.X}`/`{standards.X}`/`{域词.X}` 均由该文件取值。（2026-11-19 三段嵌套化：`naming/域词/白名单` 物理归 `业务线.{业务线.当前线}` 段下，占位符按当前线解析）**无该文件→降级通用模式**：文档目录=workspace`需求文档\`、命名按通用式（`{产品}_{模块}_…`）、正本=手艺包`01_标准\`、编号 N/Q/F，并提示用户先建配置（模板=手艺包`04_技能包\agent-company.example.json`）；禁凭旧记忆硬写公司路径。

**阶段⓪ 角色自检（L0，2026-11-10 接线）**：接需求先过《{standards.L0_角色}》（降级=通用包标准 §0.5）——**先问全谱系**（功能/UI/性能/兼容/安全/体验，无明确要求的主动提出建议，执行纪律1）；答疑姿态=主动挑战模糊/矛盾需求（缺陷预防②）；谱系结论带入后续 BRIEF。

**阶段⓪.5 需求接收与分诊（2026-11-11 接线，《{standards.L5_治理}》§1）**：拿到需求先出**需求接收卡**（变更类型/影响面/业务目标/明确不测/责任人/关联资产）并判**入口档位**——轻量/标准/完整，判据与最低流程见治理标准 §1.1（完整档判据词表={域词.分诊完整档判据}；他行业按各自高风险词表同位套用；单菜单低风险小改=轻量档）。档位结论与理由写进理解说明文首，随谱系结论一并带入 BRIEF 与 pipeline 编排（轻量档触发 usecase-pipeline 短路规则）；**分诊发生在答疑之前**——档位决定答疑深度与用例流程深度，不是设计期再补。

**阶段⓪.6 开发知识库预扒（2026-11-17 接线，公司层 `integrations.knowledge_base`）**：通读需求后、发现疑问**前**，按本菜单名/功能词/接口名预扒开发知识库（`{paths.公司包}/tools/wk_kb.py search "<菜单名> <功能词>"`，QA/RB/IF/SC 四类卡）——产出两用：①**系统现状引证**进理解说明（引卡必带编号如 RB-004／IF-waybill-send-bill，可审计）；②**提问升级**——开放式疑问变“开发库卡显示系统按 X 处理，请确认按 X 还是有新口径”的确认式（部分问题从问用户降为带证据确认）。**红线：卡片＝系统现状侧证据，永不替代拍板**——“开发库说系统就这样”不构成预期口径；**卡未覆盖→直读源码**（`integrations.dev_git` 财务 29 仓，**按 dev_git 同步策略先绑定用户指定当前分支，再只读审计**：枚举全集读枚举类、入参校验读 Controller/DTO、状态流转读 Service——代码＝一手现状，引用带`仓:分支:类:行号`）；两源均不可用/无果→跳过记 BLOCKED，不阻塞答疑。


**⏱ 计时打点（《计时与时间线规范》v1.2·2026-11-25 接入）——开工第一步／收工最后一步，本技能管 ⓪需求熟悉 与 ①答疑 两段：**

```bash
# 先把 {paths.Agent本体} 解析成 agent-company.json 里的绝对路径，再执行；<册名>＝流水线台账里的需求名，同一需求各阶段沿用同名
python -X utf8 "{paths.Agent本体}/tools/timeline_mark.py" begin --id "<册名>" --phase locate --actor requirement-qa-loop
python -X utf8 "{paths.Agent本体}/tools/timeline_mark.py" end   --id "<册名>" --phase locate --actor requirement-qa-loop --artifact "<理解说明路径>" --evidence "接收卡＋定位结论＋首批疑问清单"
python -X utf8 "{paths.Agent本体}/tools/timeline_mark.py" begin --id "<册名>" --phase qa --round "第N问" --actor requirement-qa-loop
python -X utf8 "{paths.Agent本体}/tools/timeline_mark.py" end   --id "<册名>" --phase qa --round "第N问" --actor requirement-qa-loop --artifact "<理解说明路径>" --evidence "闭环表第N项"
```

- **位置**：`locate`＝拿到需求、角色自检之前 begin → 接收卡／定位结论／首批疑问成形、发出第一问之前 end；`qa` 每问一段＝收到用户答复即 begin → 消化、回写理解说明、下一问成形之后、发出之前 end；§4.5 完备性质疑＝`--round "完备性质疑"`、§5 两层抽离＝`--round "标准抽离"`、终检与规划摘要＝`--round "终检·规划摘要"`，各一段；
- 工具打印的 `⏱` 行**原样转述给用户**（开始一行随本轮首句，结束一行随提问／汇报）；耗时取底账自动算（不含用户答复等待），**禁手填、禁事后补造**；被打断／中途停机同样先 end（`--note` 写原因），续做重新 begin；整段漏记只能 `miss --id "<册名>" --phase <码> --reason "…"` 如实申报。

目标：把需求原文变成**零待拍的《理解说明》**和**两层标准**（域标准 + 通用正本增量提案），为 `usecase-pipeline` 供料。纪律：疑问在设计用例前全部拍板闭环不留尾巴；标准内的助手自查自纠主动报，标准外/不合理的提请拍板。

## 1. 通读与疑问发现（五面 + 四源）

Read 需求原文（`{paths.需求文档}\{naming.需求文档模式}`，用最新版）与已有理解说明（若有）。按五个面扫疑问：
- **结构面**：菜单/页签/列/字段/按钮——原文写了但没说清的（如列序、空值形态）；
- **流程面**：业务流/事件流/状态流转——只写了一半的（如部分取消、时序先后）；
- **权限面**：行/列/操作/越权路径、机构树形态；
- **边界面**：枚举全集、上限/边界、组合与互斥、时区与闭开区间；
- **架构面**：与上游/同族系统的取数与联动（谁推事件、字段取谁的当前值、异步链路）。

再按覆盖度四源补扫（正本 §14）：原文功能性表述是否每句可测；上游同族需求的特殊规则（累计/封顶/豁免/特殊属性）在本菜单如何体现；拍板两两交叉是否出新场景；操作时序对与越权路径。

疑问分级：**必须拍板**（口径空白/内部矛盾/两种方案二选一）vs **可按推论+转测校准走**（展示细节、实际档位值）——后者不要拿去烦用户，挂进理解说明"转测校准清单"。

**适用范围四轴（2026-11-20 接总库·答疑必问）**：五面扫完，另按四轴确认本需求的适用范围，取值对齐总库主数据单一来源（绝对路径全文，禁缩写成相对路径）：

```bash
# 先把 {paths.Agent本体} 解析成 agent-company.json 里的绝对路径，再执行；禁止把占位符或相对路径直接交给 shell
python -X utf8 "{paths.Agent本体}/tools/case_library.py" metadata
```

- **业务线**：取公司配置 `业务线.当前线`（如快运）；
- **租户**：从主数据 `tenants` 候选里选（现为 快运 / 仓链 / 财务中心，后续以文件为准）——多租户或 ALL 要当用户口径拍板；
- **客户范围**：对齐 `customer_scopes`（现仅 STANDARD）；**产品版本主数据尚未提供**，暂不强问；
- **口径纪律**：任一轴未知 → 先置 `PENDING_SCOPE`，**禁止默认 ALL**（方案 §14.1），记进理解说明"适用范围"章节，随拍板回写；
- **降级**：主数据文件读不到 → 记 BLOCKED，四轴照问但不填候选值，不阻塞答疑主流程；
- 四轴结论带入 BRIEF，供用例落库时 scope 字段取值，避免 315 条用例 scope 长期 `PENDING_SCOPE` 空着。

## 2. 逐条提问（对话内五段式·一次一问）

**一律在对话内逐条展示、用户文字回复；禁用 AskUserQuestion 选择框**（用户明确反馈过：选择框一次装不下多问、且限制表达）。一次只问一个主题，格式见 `references/qa-formats.md`（2026-11-02 对齐上游通用规范 v25 §12.5 升五段式）：

> 【疑问】一句话歧义点 → 【需求原文】引原句标章节不改写（附已拍板相关口径表，防同题重问）→ 【我的理解】多种可能解读并列 → 【解决方案】**全部候选方案**（含倾向），每个给足细节（用例断言口径/影响范围/组合场景），**附我的建议与理由**——用户只做选择题、不做问答题 → 【对用例设计的影响】不同选择改变哪些用例/断言/场景。

方案**详尽优先**——宁可多给备选与推演，不可只给模糊方向。用户给的方案若超出预设选项（常见且往往更好），按用户口径落，别硬套选项。**闭环纪律**：拍板即登记进理解说明对应章节，不得同题反复追问。

## 3. 拍板回写《理解说明》

- 文件：`{paths.需求文档}\{naming.理解说明模式}`，骨架见 references。
- **只新增不覆盖**：旧结论不删，用"→ 修正（日期）：新口径"追加；被修订的旧句划线标注。版本号递增记录在文首与修订处。
- 编号体系：疑问按 N/M/F 递增（或沿用该需求已有体系），**十一、答疑闭环记录**表每项一行（疑问/结论/拍板时间）；文首计数与文尾版本约定同步。
- 正文分主题章节（结构/判定矩阵/机制/权限/导出…），拍板口径写进对应章节而不是只留在表里——用例生成读的是章节。
- 拿不准的观察项挂"转测校准清单"（编号①②…），注明按什么方向理解、执行时观察什么。
- **理解说明的修改属标准更新**：复检类修订（改旧句）须用户确认后才动；新拍板直接入。

## 4. 终检（零待拍才算闭环）

按 references 终检清单过一遍：文内无"待确认/待拍板"残留；拍板之间无互相矛盾（尤其修正前后）；原文每句功能表述有口径或挂了转测校准；四源扫一遍无新疑问；闭环表计数=文首计数。发现新疑问回第 2 步。

## 4.5 独立完备性质疑（2026-11-18 立·自查终检之上的对抗 pass）

自查终检=按清单问（容易顺着已有框架看漏）；本步=**spawn 独立子代理反读需求原文**，只给需求文档+已闭环的理解说明，**不给提问过程**，以"生成方马上要拿它造用例"的破坏视角找漏问：
- 四类缺口：①**未定义行为**（功能说了但边界/异常分支无口径）②**歧义口径**（同词多处不同义/可两读）③**状态未说明**（生命周期/并发/时序交互没交代）④**隐含前提**（需求默认了但没写的环境/主数据/权限假设）；
- 输出漏问清单（每条：原文位置/缺口类型/建议问法）→ 回流第 2 步逐条拍板至零；
- 判据：质疑方找不到新漏问（或仅剩转测校准类）=完备性闭环；与外部用例对比（external-compare 的"别人想到我没想到"）互为内外两道补漏。
- 用量纪律：新需求首次答疑必跑；小需求/纯维护类可声明豁免（记录在理解说明 footer）。

## 5. 两层抽离

1. **域标准**（`{paths.需求文档}\{naming.域标准模式}`，文件名**不带需求版本号**、跨版本复用）：从理解说明抽九大块——§一固定枚举与控件、§二业务对象常量表（含**来源菜单特殊规则→本菜单呈现映射**）、§三结构常量、§四处理链路、§五判定规则表、§六断言锚点口径、§七转测校准清单、§八 PRE 依赖、§九组织约定。文首声明：通用方法按{standards.通用正本统称}、本文只管域规则、冲突以理解说明为准。
2. **通用增量提案（G 条目）**：本次答疑沉淀的可跨需求复用写法（参照通用正本 §13 的先例），列成提案表（条目/内容/来源拍板/建议落点），**须用户拍板后**才以"只新增不修改"写进{standards.通用正本统称}（递增版本、修订记录注明来源），随后域标准里改为引用。
   - 域标准只落活正本（{paths.需求文档}），**不镜像入 agent 仓**（2026-11-25 用户拍板：agent 仓只放标准与流程；域标准=特定需求的业务口径，属业务数据；仓内 L4域标准/ 目录已撤销）
3. 更新项目记忆（拍板数/关键口径/待办）。

## 硬规则

- 拍板对话内逐条、不用选择框；用户原话口径优先于我的预设选项。
- 只新增不覆盖；转测校准用"观察XX"句式；不臆断为肯定断言。
- 域标准不复制通用正本内容，只引用；理解说明是唯一设计依据。
