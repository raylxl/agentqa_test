# 需求答疑闭环与标准抽离（阶段①②）

## 0. 公司适配层（开工第 0 步·2026-11-13 参数化）

读 workspace `公司包/agent-company.json` 解析公司值；下文 `{paths.X}`/`{naming.X}`/`{standards.X}`/`{域词.X}` 均由该文件取值。**无该文件→降级通用模式**：文档目录=workspace`需求文档\`、命名按通用式（`{产品}_{模块}_…`）、正本=手艺包`01_标准\`、编号 N/Q/F，并提示用户先建配置（模板=手艺包`04_技能包\agent-company.example.json`）；禁凭旧记忆硬写公司路径。

**阶段⓪ 角色自检（L0，2026-11-10 接线）**：接需求先过《{standards.L0_角色}》（降级=通用包标准 §0.5）——**先问全谱系**（功能/UI/性能/兼容/安全/体验，无明确要求的主动提出建议，执行纪律1）；答疑姿态=主动挑战模糊/矛盾需求（缺陷预防②）；谱系结论带入后续 BRIEF。

**阶段⓪.5 需求接收与分诊（2026-11-11 接线，《{standards.L5_治理}》§1）**：拿到需求先出**需求接收卡**（变更类型/影响面/业务目标/明确不测/责任人/关联资产）并判**入口档位**——轻量/标准/完整，判据与最低流程见治理标准 §1.1（完整档判据词表={域词.分诊完整档判据}；他行业按各自高风险词表同位套用；单菜单低风险小改=轻量档）。档位结论与理由写进理解说明文首，随谱系结论一并带入 BRIEF 与 pipeline 编排（轻量档触发 usecase-pipeline 短路规则）；**分诊发生在答疑之前**——档位决定答疑深度与用例流程深度，不是设计期再补。


目标：把需求原文变成**零待拍的《理解说明》**和**两层标准**（域标准 + 通用正本增量提案），为 `usecase-pipeline` 供料。纪律：疑问在设计用例前全部拍板闭环不留尾巴；标准内的助手自查自纠主动报，标准外/不合理的提请拍板。

## 1. 通读与疑问发现（五面 + 四源）

Read 需求原文（`{paths.需求文档}\{naming.需求文档模式}`，用最新版）与已有理解说明（若有）。按五个面扫疑问：
- **结构面**：菜单/页签/列/字段/按钮——原文写了但没说清的（如列序、空值形态）；
- **流程面**：业务流/事件流/状态流转——只写了一半的（如部分取消、时序先后）；
- **权限面**：行/列/操作/越权路径、机构树形态；
- **边界面**：枚举全集、上限/边界、组合与互斥、时区与闭开区间；
- **架构面**：与上游/同族系统的取数与联动（谁推事件、字段取谁的当前值、异步链路）。

再按覆盖度四源补扫（正本 §14）：原文功能性表述是否每句可测；上游同族需求的特殊规则（累计/封顶/豁免/特殊属性）在本菜单如何体现；拍板两两交叉是否出新场景；操作时序对与越权路径。

疑问分级：**必须拍板**（口径空白/内部矛盾/两种方案二选一）vs **可按推论+转测校准走**（展示细节、实际档位值）——后者不要拿去烦用户，挂进理解说明"转测校准清单"。

## 2. 逐条提问（对话内五段式·一次一问）

**一律在对话内逐条展示、用户文字回复；禁用 AskUserQuestion 选择框**（用户明确反馈过：选择框一次装不下多问、且限制表达）。一次只问一个主题，格式见 `references/qa-formats.md`（2026-11-02 对齐上游通用规范 v25 §12.5 升五段式）：

> 【疑问】一句话歧义点 → 【需求原文】引原句标章节不改写（附已拍板相关口径表，防同题重问）→ 【我的理解】多种可能解读并列 → 【解决方案】**全部候选方案**（含倾向），每个给足细节（用例断言口径/影响范围/组合场景），**附我的建议与理由**——用户只做选择题、不做问答题 → 【对用例设计的影响】不同选择改变哪些用例/断言/场景。

方案**详尽优先**——宁可多给备选与推演，不可只给模糊方向。用户给的方案若超出预设选项（常见且往往更好），按用户口径落，别硬套选项。**闭环纪律**：拍板即登记进理解说明对应章节，不得同题反复追问。

## 3. 拍板回写《理解说明》

- 文件：`{paths.需求文档}\{naming.理解说明模式}`，骨架见 references。
- **只新增不覆盖**：旧结论不删，用"→ 修正（日期）：新口径"追加；被修订的旧句划线标注。版本号递增记录在文首与修订处。
- 编号体系：疑问按 N/M/F 递增（或沿用该需求已有体系），**十一、答疑闭环记录**表每项一行（疑问/结论/拍板时间）；文首计数与文尾版本约定同步。
- 正文分主题章节（结构/判定矩阵/机制/权限/导出…），拍板口径写进对应章节而不是只留在表里——用例生成读的是章节。
- 拿不准的观察项挂"转测校准清单"（编号①②…），注明按什么方向理解、执行时观察什么。
- **理解说明的修改属标准更新**：复检类修订（改旧句）须用户确认后才动；新拍板直接入。

## 4. 终检（零待拍才算闭环）

按 references 终检清单过一遍：文内无"待确认/待拍板"残留；拍板之间无互相矛盾（尤其修正前后）；原文每句功能表述有口径或挂了转测校准；四源扫一遍无新疑问；闭环表计数=文首计数。发现新疑问回第 2 步。

## 5. 两层抽离

1. **域标准**（`{paths.需求文档}\{naming.域标准模式}`，文件名**不带需求版本号**、跨版本复用）：从理解说明抽九大块——§一固定枚举与控件、§二业务对象常量表（含**来源菜单特殊规则→本菜单呈现映射**）、§三结构常量、§四处理链路、§五判定规则表、§六断言锚点口径、§七转测校准清单、§八 PRE 依赖、§九组织约定。文首声明：通用方法按{standards.通用正本统称}、本文只管域规则、冲突以理解说明为准。
2. **通用增量提案（G 条目）**：本次答疑沉淀的可跨需求复用写法（参照通用正本 §13 的先例），列成提案表（条目/内容/来源拍板/建议落点），**须用户拍板后**才以"只新增不修改"写进{standards.通用正本统称}（递增版本、修订记录注明来源），随后域标准里改为引用。
3. 更新项目记忆（拍板数/关键口径/待办）。

## 硬规则

- 拍板对话内逐条、不用选择框；用户原话口径优先于我的预设选项。
- 只新增不覆盖；转测校准用"观察XX"句式；不臆断为肯定断言。
- 域标准不复制通用正本内容，只引用；理解说明是唯一设计依据。
