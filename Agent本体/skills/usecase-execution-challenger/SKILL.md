# usecase-execution-challenger 执行判定质疑方（2026-11-18 立·执行质疑标准 v1 B案落地）

## 0. 公司适配层（开工第 0 步）

读 workspace `公司包/agent-company.json` 解析 `{paths.X}`；无该文件→降级通用模式（本技能主输入=文件路径参数，天然通用）。输入四件：
- **账本**：执行结果 jsonl（同 TC 多轮取**末次**判定）
- **规格**：机器规格 json（执行器实际吃的 specs；无规格文件时以账本 detail+证据件为准）
- **证据件目录**：逐条证据 json（报价/推单/计算流水/断言五层；缺证据=复核结论直接标"证据不足"）
- **用例册 MD**：正本（#### TC- 块 + 前置条件/操作步骤/预期结果 竖排五行——分层标准 L3 通用形态）

## 定位与独立性四铁律（标准 §二）

1. **实例隔离**：质疑方=spawn 独立子代理，不继承生产方（执行器）会话结论——执行器自述"通过"对质疑方是零信息；
2. **证伪立场**：任务是推翻判定，不是确认；假设生产方有错，逐条找证据；
3. **信息隔离**：只给数据文件（复核包+证据件+册原文），不给生产方的推理过程与口头结论；
4. **两道出口分离**：出口一=维持（附独立依据）；出口二=改判/判无效（附根因+建议处置）。禁"大概没问题"类模糊出口。

## 工作流五步

### 1. 复核包生成
```
python <skill>/scripts/gen_review_packets.py --ledger <账本.jsonl> --specs <规格.json> --evid <证据目录> --md <册.md> --out <输出目录> [--group tab|prefix|batch]
```
每包 jsonl 一行一例：tc/title/pre/step/exp（册原文）+ spec（实际规格）+ verdict/摘要（末次判定）+ evid_exists。**同 TC 多轮判定必须取末次**（复测/复评覆盖语义）。

### 2. 分路派质疑子代理
按页签/分章/批次分路（每路 20~90 条为宜），并行 spawn。**prompt 模板（六核查维度，全条目覆盖禁抽样）**：
> 你是{需求名}执行结果的独立质疑方（对抗性质疑立场，执行方不自证）。对全部 N 条判定逐条复核——通过和失败都要，BLOCKED 只核跳过原因与原文相符性。
> 数据：复核包 {path}（tc/pre/step/exp=册原文，spec=执行规格，verdict=判定）；证据件 {evid}/{TC}.json。
> 背景口径注入（调用方必填三件）：①本域已知系统差异族清单（失败属正常证据不算执行问题的边界）②关键枚举/口径值（如订单类型映射、费项码）③本轮开发/用户反馈焦点（如"订单与报价信息不一致"→逐条核对维度 vs 推单参数）。
> 每条六查：a) 册原文独立重推预期（金额公式/命中/无费用）；b) 规格忠实性（维度/明细数值/数量/类型/事件——失真即标"规格失真"）；c) 证据件支持性（calcRows 金额/状态/命中是否支撑判定；dimNotes 有无未解释错位）；d) 维度一致性（报价维度 vs 推单参数，no_fee 反例除外）；e) 已知差异族对照（归族是否成立）；f) BLOCKED 跳过原因 vs 原文。
> 输出 {out}/复核结果_{路名}.md：先汇总表（确认/无效/改判/存疑计数+根因分类），再逐条表 | TC | 册判定 | 复核结论 | 一句话依据 | 建议处置(维持/改判通过/改判失败/需修规格重跑) |，BLOCKED 合并小节。只读环境，除输出文件外不写任何文件。

### 3. 聚合双账本
| 结论 | 定义 |
|---|---|
| 确认 | 复核独立重推+证据核对后采信（通过/失败各自计） |
| 无效待重跑 | 执行侧构造失真（规格失真/造数污染/场景截断/跳过理由不成立）——**不代表系统行为，禁直接报缺陷** |
| 合法跳过 | 跨菜单依赖/按场景通道矩阵已授权的 Mock 事件造数不可用/真实界面构造缺口（须给证据，如接口清单或 UI 操作实录；DB 仅可只读取证。界面造数场景不得降级为 Mock 代建报价/政策） |

### 4. 争议处置
- **改判类**：生产方复核质疑依据→确认后以"复评行"落账本（标注复评依据），可离线复评（证据件重跑断言逻辑，无需重执行）或抽样重执行（标准 §3.4）；
- **无效类**：按根因清单回流规格/造数修复→定向重跑（禁全量盲重跑）；
- 子代理汇报"全部确认/复核通过"**必须附完整逐条表**，无表不可信。

### 5. 报告投影
双账本表+复核发现（根因分类+系统差异实锤清单+整改清单）作为报告固定节；报告判定口径声明"确认/无效"双账本，禁只报执行面原始过/败数。

## 首战校准（2026-11-18 仓内计费 R2·固化参数）

- 五路（按页签）并行复核 296 条：**推翻 180 失败中的大半=我方规格失真**（最低/最高收费组序错绑、多报价压缩、专造仓编码截断同码、物料编码填名、双单只推 A）——**规格保真是最高频失真源，建议前置"规格保真门"（规格生成后、执行前）拦在烧执行轮之前**；
- 断言语义坑先验：影子行（如拦截链二次计算 NO_QUOTE）连坐误败——复核发现后按"只认 OK 行"复评改判 6 条；
- 复核包必须在**全部回收轮结束后**生成（否则末次判定失真）；生成后如又有复评改判，聚合时以账本末次为准并标注复核时效。

- **横排册复核包**：竖排提取器（gen_review_packets.py）在横排五行表册会抓到表头行（YZ/CC 补账实证：pre/step/exp 全为"操作步骤|预期结果|…"碎片，首轮复核作废重做）——横排册一律改用 jt_exec/extract_packets.py（横排数据行提取）+build_routes.py 分路+aggregate_challenger.py 聚合（含 kind=空复评行的末次判定口径）。

## 纪律
- 触发即全量：说"复核判定"就是对整轮全部判定，禁抽样复核（抽样重执行是标准 §3.4 的补充手段，不是复核本身的抽样）；
- 复核方不修任何生产文件（用例/规格/账本）——改判经生产方确认后由生产方落；
- 与 usecase-qc 分工：本技能质疑**判定本身**（对不对），qc 质疑**交付链**（载体一致性/回写锚点/报告合规）；两道门都要过。
