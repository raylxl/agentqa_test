# 需求流水线总调度（orchestrator·2026-11-13 立）

## 0. 公司适配层（开工第 0 步·2026-11-13 参数化）

读 workspace `公司包/agent-company.json` 解析公司值；`{paths.X}`/`{standards.X}`/`{环境.X}` 由该文件取值（台账路径/机检脚本/考古源均配置化）。**无该文件→降级通用模式**：台账=workspace`需求流水线台账.md`（无则建），考古源按目标系统可得资源裁剪；禁凭旧记忆硬写公司路径。

## 定位与分工（不造重叠的壳）

- **台账**＝状态正本：`{paths.需求流水线台账}`（活区可更、事件日志只增）；
- **本技能**＝跨段状态机：读台账 → 验门 → 调环节技能 → 更台账 → 停机。**只做调度，不干环节内的活**；
- **环节技能**＝手脚（一律不改）：qa-loop（①答疑）/ generator（②生成）/ spec-gate（②生成后规格保真门）/ challenger（③设计稿质疑）/ 交付工具链（④，经 usecase-pipeline）/ executor（⑤执行）/ execution-challenger（⑤收尾判定质疑门）/ feedback-loop（⑥反馈）/ defect-challenger（提单前缺陷质疑门）/ usecase-qc（⑦独立质检）。四道门调用时点：spec-gate＝规格生成后开批前；execution-challenger＝每轮执行收尾、进反馈闭环前；defect-challenger＝任何缺陷提单动作前；usecase-qc＝收官放行前。
- **usecase-pipeline**＝资产宿主＋设计段编排（BRIEF/矩阵/证书/assemble 住那），本技能在其上做跨段调度，不替代。

## 开工第 0 步·验门（每次"跑/继续"必走）

1. 读台账该线状态行 → 按台账 §二 查**上一段出口门的文件证据**（证书存在？report_sync 绿？两节已更？）；
2. **门没过 → 不推进**，输出差什么、差在哪（上轮没结账禁开新段——executor 硬闸思想全局化）；
3. 首次调度该线（或距上次调度>1天）→ 先回查该册测试报告「当前余项清单」+「呈报-拍板台账」两节，校准台账状态行再动（多会话并行，台账可能滞后）。
4. **质疑门开工巡检（2026-11-20 立·整改③）**：`python {paths.执行工具}/gate_scan.py` 退出码 0 才推进——扫全部在途册，生效后轮次缺质疑门覆盖即红；红=先安排补账（execution-challenger）再推进该线执行段，禁带病开新轮。

## 推进粒度（各段不同，禁贪全链）

| 段 | 粒度 |
| --- | --- |
| ①答疑 | **一问一停**（对话文字拍板，禁选择框） |
| ②③④ | 段内连跑：生成→质疑修复循环→证书→三格式差异=0，段末汇报 |
| ⑤执行 | **一轮一停**：报告产出即停 |
| ⑥反馈 | 呈报一停：四源盘点→五段式呈报（场景/操作/预期/实际/消息原文）→挂拍板队列→停 |
| ⑦收尾 | usecase-qc 独立质检（六查证伪→红清零＋复检绿＝放行）；坑库沉淀/回写候选/置信度已在⑤尾部完成，放行后停机等签字 |

## 收尾动作（每次停机前必做，顺序固定）

1. 更新台账 §一 状态行（阶段/断点/下一步/时间）＋ §四 事件日志追加一行；
2. 有待拍板 → 登记台账 §三 拍板队列；
3. 输出停机卡。

## 逆向启动（无需求文档入口·2026-11-13 立·用户拍板"落"）

触发＝只有菜单/界面、无需求文档（"测这个菜单"类指令）。缺需求只影响入口两段，②起六段不变。

**⓪' 现场考古**（agent 自主干，产出＝观察到的事实清单；六源按序，按目标系统可得资源裁剪）：
1. **需求库考古优先**：{paths.需求文档} 历史库全文搜菜单名/相近名——多数新菜单可能有前身需求；有前身则以前身为底本、以现状差异为增量提问。
2. **开发知识库检索（可选适配器）**：按公司 profile `integrations.knowledge_base` 声明的能力调用；未配置或不可用时跳过并记录 BLOCKED，不猜测 provider/tool 名称。
3. 界面遍历：{环境.登录技能}（{环境.chrome端口.用户交互主实例}）→ {环境.租户体系} → 开菜单脚本；字段/必填/长度格式、按钮、弹窗、列表列、筛选器、导入导出、状态流转、提示文案；
4. 历史用例：总用例库＋usecase-external-compare 圈参考范围；
5. DB 反推（连接信息不入本文件，见 integrations.database）：**严格只读**，仅 SELECT/SHOW/DESCRIBE/DESC/EXPLAIN 查表结构/枚举值/关联（反推数据模型与状态机）；
6. 接口抓包：CDP 抓请求看入参出参、前后端校验分工。

**①' 需求重建（逆向稿两栏铁律）**：写《需求理解说明（逆向稿）》——
- 「系统现状」栏＝客观观察，只陈述；
- 「我的推断」栏＝规则假设，**逐条拍板后才升格为"预期"**——现状≠断言，防把 bug 测成 PASS（考古提供问题清单，答案从拍板来）；
- 疑问句式变化：从"需求这么说对吗"改为"系统表现为 X，预期应为 Y 吗"。

**两个克制点**：
1. 范围圈定：观察到的≠都要测，本次测试边界与用户拍板圈定（先例：仓内"按钮权限配置"＝AI 自加被砍）；
2. 全谱系必问（L0）：只给界面时更易漏——功能/UI/性能/兼容/安全/体验测哪几维必须问并记理由。

拍板闭环后逆向稿即理解说明正本，并入②生成起正常流水线。**考古完成＝停机点**（呈逆向稿两栏给用户逐条拍）。

## 硬规则

1. **单次只推进一条线**到下一个停机点（防上下文膨胀）；多线并行=逐线逐次调用；
2. 执行段（⑤）调起前：查 {环境.chrome端口.runner独占} 独占实例锁＋心跳（G36 多会话撞车教训）；AI 执行走 cdp_pool {环境.chrome端口.无头AI执行}；
3. 拍板一律对话内逐条文字，**禁 AskUserQuestion**；
4. 环节技能产出异常不现场调试：标 BLOCKED、记台账、跑该线下一步或停机呈报（5 分钟规则的全局化）；
5. 台账结构改动（§二阶段字典等）须用户拍板后升版；日常状态更新不升版；
6. 质疑段（③）子代理与生成方实例隔离；执行结果质疑按《执行质疑标准_v1.1》在报告终版前挂点。

7. **正本现读现用**（防会话缓存过期）：引用标准/台账/报告内容一律**现读磁盘文件**为准，禁凭本会话早前读入当依据；跨段推进（第 0 步验门）时重读关键正本——文件被改过也不依赖"谁通知谁"；
8. **改配置必宣告**（提醒责任在改动方）：凡改动 mcp.json、技能 frontmatter/触发词等"需重开会话生效"的配置，收尾输出必含一行"⚠需重开会话生效：{文件}"——不靠用户记得；
9. **版本一致性机检**：标准/技能升版后跑 `{paths.标准体系}\standards_version_check_v1.py`（00_索引锚点 vs 各文件修订记录 vs 技能引用版本），红了禁带旧版本号引用。
