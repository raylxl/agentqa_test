# 测试执行结果判定标准 v1

> **定位**：定义测试用例执行后如何判定结果（PASS/FAIL/NOT_EXECUTED/BLOCKED），以及每个判定需要什么证据。适用于所有 UI 功能测试执行（人工+自动化）。
> **来源**：2026-11-08 用户质疑"你说通过了我就认为是通过的，你拿什么判定这用例执行后是通过的？"
> **核心原则**：**判定基于系统做了什么，不是基于脚本做了什么。**

---

## 一、测试执行生命周期

```
① 前置准备 → ② 执行操作 → ③ 观察结果 → ④ 比对预期 → ⑤ 采集证据 → ⑥ 判定结果
   造数/导航     点击/填入     读系统状态    与用例预期比对   截图/记录      出结论
```

**关键区分**：
- ② 执行操作 = 测试人员（或脚本）对系统做了什么
- ③④ 观察比对 = **系统**返回了什么、与用例**预期**是否一致
- 判定结果只能基于③④，不能基于②

> "我的脚本点完了按钮" ≠ "系统处理了请求"
> "我的脚本没报错" ≠ "系统行为正确"
> "我的脚本超时了" ≠ "系统有问题"

---

## 二、结果分类与判定条件

### 2.1 PASS（通过）

**定义**：测试执行到了验证点，系统的实际行为与用例预期一致。

**判定条件（三个必须同时满足）**：

| # | 条件 | 说明 |
| --- | --- | --- |
| 1 | **操作到达验证点** | 用例的关键步骤执行完毕（如：点完了保存/提交/删除按钮） |
| 2 | **观察到了系统行为** | 读取到了系统的可观测状态（弹窗关闭/列表出现新数据/拦截提示文本/输入框回显值/审核状态变化） |
| 3 | **行为与预期比对通过** | 观察到的值/状态/文本与用例"预期结果"列写的**具体值**一致 |

**禁止标 PASS 的情况**：
- 操作没报错但**没检查系统返回了什么**（`any` 断言）
- 只验证了"弹窗关闭"但**没验证保存的数据对不对**（需配合列表/详情比对）
- 只验证了"有提示"但**没验证提示内容**是否与预期一致

### 2.2 FAIL（失败）

**定义**：测试执行到了验证点，系统的实际行为与用例预期**不一致**。

**判定条件（三个必须同时满足）**：

| # | 条件 | 说明 |
| --- | --- | --- |
| 1 | **操作到达验证点** | 关键步骤执行完毕，系统收到了请求 |
| 2 | **观察到了系统行为** | 系统返回了可观测的响应（弹出了提示/返回了数据/状态发生了变化） |
| 3 | **行为与预期比对不通过** | 观察到的值/状态/文本与用例预期**明确不一致** |

**必须记录**：
- **预期值**：用例预期结果列写的具体内容
- **实际值**：系统实际返回/展示的具体内容
- **差异说明**：哪里不一致
- **证据**：截图或日志（证明系统确实返回了这个值）

**禁止标 FAIL 的情况**：
- 脚本超时/页面没加载/元素找不到（这是 NOT_EXECUTED，**系统行为未知**）
- 操作没执行完就断了（同上）
- 断言写错了（比如断言了一个不存在的列名）

### 2.3 NOT_EXECUTED（未执行）

**定义**：测试没有到达验证点，无法观察系统行为，**无法得出任何结论**。

**判定条件（任一即可）**：

| 情况 | 说明 | 最终结果 |
| --- | --- | --- |
| 页面未加载/元素不可达/操作中断/超时 | 未到达验证点，系统行为未知 | `NOT_EXECUTED` |
| 前置数据或依赖服务未就绪 | 属于执行通道外部阻断，需记录责任人和补齐动作 | `BLOCKED` |
| 工具不支持、必须人工下载/人工验证 | 自动通道受阻，转人工队列 | `BLOCKED` |
| any/无实质断言 | 操作完成但没有有效验证 | `NOT_EXECUTED` |

**NOT_EXECUTED 的纪律**：
- **禁写风险暗示**（如“可能影响金额准确性”）——没有证据不给判断
- **处置=列人工补测清单**——写清楚"要验证什么+怎么操作+预期什么"
- **不参与通过率计算**——分母中排除

### 2.4 BLOCKED（受阻）

**定义**：测试通道被环境/工具/数据限制阻断，已知原因且非系统缺陷。

| 情况 | 举例 |
| --- | --- |
| 环境限制 | 导出需手动到导出任务页查询下载 |
| 数据不足 | 角标 99+ 测试需 100+ 条数据 |
| 工具限制 | 文件上传组件与自动化工具不兼容 |
| 依赖缺失 | 需要的测试账号/配置/接口未就绪 |

## 三、断言强度分级

| 级别 | 断言类型 | 验证了什么 | 可否独立判 PASS |
| --- | --- | --- | --- |
| **强** | 列值逐行匹配（colAllMatch） | 列表每一行某列都等于预期值 | ✅ 可 |
| **强** | 导入成功+列表查到（impOk） | 导入结果页"成功" + 列表有该条数据 | ✅ 可 |
| **强** | 行列值精确断言（rowColVal） | 指定行的指定列=预期值 | ✅ 可 |
| **强** | 输入框回显（msEcho/echo） | 输入后输入框实际值=预期修正值 | ✅ 可 |
| **强** | 表头完整性（headCols） | 列头与需求列名逐一匹配 | ✅ 可 |
| **强** | 默认值核对（formDefault） | 各字段默认值与预期一致 | ✅ 可 |
| **中** | 弹窗关闭（dlgGone） | 弹窗关闭了（保存类操作可能成功） | ⚠️ 需配合列表查询 |
| **中** | 拦截提示出现（blocked） | 出现了错误提示 | ⚠️ 需验证提示内容含预期关键词 |
| **中** | 列表含某文本（rowHas） | 某行包含某文本 | ⚠️ 弱于列值精确匹配 |
| **中** | 总条数（total/empty） | 分页总数/空态 | ✅ 可（对于查询用例） |
| **强** | 接口值断言（apiVal，L3） | 响应业务字段=预期值（数值按值比较，1000.5=1000.50；2026-11-15 接口通道立） | ✅ 可 |
| **强** | 接口结构断言（apiStruct，L2） | 响应字段存在且类型合法（动态字段降级口径=存在且格式合法） | ✅ 可（结构型用例，如同 headCols） |
| **中** | 接口状态断言（apiStatus，L1） | HTTP 200 且业务 code 成功 | ⚠️ 仅证明链路通，禁单独判 PASS（细则 §十六） |
| **弱** | 弹窗保留（dlgStay） | 弹窗还开着（可能被拦截） | ❌ 需配合 blocked |
| **弱** | 弹窗标题（dlgTitle） | 标题文本匹配 | ⚠️ 仅证明弹窗打开 |
| **无** | any/totalAny | **什么都不验证，必过** | ❌ **禁标 PASS** |

## 四、证据要求

| 结果 | 必须留什么证据 | 形式 |
| --- | --- | --- |
| PASS | 断言通过的**具体值** | "列表第1行审核状态=审核通过" / "总数=13" / "输入框读回=999999" |
| FAIL | 预期值 vs 实际值 + **截图** | "预期:保存成功; 实际:提示'最高收费必须严格大于最低收费'" + png |
| **PASS(复测)**（§5.1，2026-11-17 立） | **两轮记录**：首败证据 + 复测通过具体值 | 首败截图+预期vs实际 ＋ 复测断言通过值（附两轮执行号） |
| NOT_EXECUTED | 未到达验证点的**原因** | "脚本点击新增按钮超时8秒" / "页面body仅295字符" |
| BLOCKED | 阻断原因 + **处置建议** | "导出跳转后需手动查询（批次10 D-13）→ 人工导出+查询+下载" |

## 五、判定流程（执行引擎/人工通用）

```
执行完操作步骤
    ↓
到达验证点了吗？
            ├── 否（超时/页面未加载/中断）→ NOT_EXECUTED
            ├── 是
                ↓
            读到了系统可观测状态吗？
                ├── 否（元素不存在/页面空白）→ NOT_EXECUTED
                ├── 是
                    ↓
                有实质断言吗？
                    ├── 否（any/无断言）→ NOT_EXECUTED
                    ├── 是
                        ↓
                    断言通过与用例预期比对？
                        ├── 是 → PASS（记录具体值）
                        ├── 否 → FAIL（记录预期vs实际+截图）

> **BLOCKED 分流**：已知外部通道限制（环境/工具/依赖/数据）在到达验证点前阻断，直接落 BLOCKED；补齐责任人与人工/重跑处置，不写成系统 FAIL。
```

### 5.1 复测改判分支（失败复测轮，2026-11-17 立用户拍板"AI复测集成进执行"）

FAIL 不是终审——批量执行循环结束后、收尾报告前，本轮全部 FAIL 条目自动进入**失败复测轮**（操作细节见你的执行细则复测轮节）。复测结果三支处置：

| 复测结果 | 终态 | 判定依据 |
| --- | --- | --- |
| ① 复测通过＋实质断言落地＋首败证据**不含**系统错误消息原文 | **PASS（披露形态"PASS(复测)"，非第五态）**：账本终态 PASS＋retest 标记，首败记录保留、报告与失败用例报告全披露"首败→复测通过"，复现率＝偶发(1/2) | 首败定性为环境/偶发误报，与出口"环境误报清零"同构——复测轮即其自动化实现 |
| ② 复测通过＋首败证据**含**系统错误消息原文（报错 toast/接口错误码原文） | **挂起·待复验**（公司账本落 SUSPEND，reason 注明"首败含系统错误原文+复测通过，矛盾证据转人工"）：进待复验清单人工定，禁自动翻案 | 复测通过≠无缺陷——真缺陷偶发（并发/时序/数据态）复测也可能通过；两轮矛盾证据不由机器裁决 |
| ③ 复测仍失败 | **FAIL 终态**：两轮证据并列入失败用例报告，复现率＝必现(2/2) | 证据更足，直接进呈报 |

**纪律**：复测轮同样适用单条 5 分钟超时、自动恢复兜底、连续 3 条环境阀；PASS(复测) 与 FAIL 的证据要求见 §四；待复验条目在出口判定按挂起逐条处置（不占 FAIL、不参与通过率分子分母口径与挂起一致）。

## 六、报告披露要求

测试报告**必须**披露以下信息，让读者能自行判断结果可信度：

| 披露项 | 说明 |
| --- | --- |
| **各状态条数** | PASS/FAIL/NOT_EXECUTED/BLOCKED 各多少条，合计=总数 |
| **PASS 断言强度分布** | 强断言多少条/中断言多少条（弱和无不许标 PASS） |
| **FAIL 分类** | 系统缺陷多少条（有证据）/ 自动化超时多少条（无结论） |
| **NOT_EXECUTED 原因分类** | 超时/数据不足/通道受阻 各多少条 |
| **真发现逐条详情** | 操作/预期/实际/证据/建议 五要素齐全 |
| **NOT_EXECUTED 补测清单** | 逐条列"要验证什么+怎么操作"（禁写风险暗示） |

## 八、推导逻辑（每条规则从测试根本目的推导）

> **测试的根本目的 = 回答一个问题："系统行为是否与预期一致？"** 以下每条规则都从这一目的推导，不是凭空定的。

### 8.1 为什么 PASS 必须观察到系统行为？

推导链：测试要回答"系统是否正确" → 要回答必须知道系统实际做了什么 → 没观察到系统行为就无法回答 → 所以不观察就不能标 PASS。

反例：118 条 any 断言标了 PASS，只证明"脚本没报错"，系统可能返回了正确也可能返回了错误——但读者以为都验证过了。

### 8.2 为什么 FAIL 必须看到系统返回了与预期不一致的东西？

推导链：FAIL 是指控"系统有缺陷" → 指控会触发缺陷单+开发排查+可能阻塞上线 → 没有证据的指控浪费别人时间 → 所以 FAIL 必须有系统实际返回的"错值"作证据。

反例：35 条超时标了 FAIL，读者以为发现了风险，实际上系统根本没收到请求。

### 8.3 为什么 NOT_EXECUTED 禁写风险暗示？

推导链：NOT_EXECUTED = 没观察到系统行为 = 不知道系统是对是错 → "不知道"意味着没有证据支持任何判断 → 写“可能影响金额”会让读者误解为"测试发现了线索" → 所以禁写。

### 8.4 为什么 any 断言禁标 PASS？

推导链：any 字面意思="不管系统返回什么都通过" → 系统可能返回错误但 any 不检查 → 标 PASS 等于说"这个场景验证过了" → 但实际什么都没验证 → 等同于虚报测试覆盖。

### 8.5 为什么断言要分四级？

推导链：不同断言验证的信息量不同 → "每行列值=预期"信息量大，"any"信息量为零 → 报告读者需要知道每个 PASS 背后的证据强度才能判断可信度 → 所以必须分级披露。

### 8.6 为什么核心原则是"判定基于系统行为而非脚本行为"？

推导链：用户让测的是系统 → 用户看报告想知道的是系统有没有问题 → 脚本行为（点没点到、有没有报错）只是手段不是结论 → 判定必须锚定在系统的可观测状态上。

## 九、对用例设计标准的反向要求（判定标准反推用例必须包含什么）

> **逻辑**：执行判定标准说"PASS 需要观察到系统行为与预期比对一致" → 那用例的"预期结果"必须写到**能被观察和比对的程度**，否则执行者不知道检查什么。

### 9.1 反推矩阵

| 判定标准要求 | 用例设计必须提供 | 现状问题 |
| --- | --- | --- |
| PASS 需要观察到系统行为 | 预期结果必须**指明在哪里看什么** | 很多条只写"保存成功"，不说到哪确认 |
| PASS 需要与预期比对 | 预期结果必须写**具体值**（不是"正确""正常"） | "正常展示""正确处理"无法比对 |
| 断言分四级，any 禁 PASS | 每条用例至少有一个**可验证的预期** | 部分用例的预期模糊到只能 any 断言 |
| FAIL 需要记录预期 vs 实际 | 预期结果必须**精确到值/文本/条数** | "拦截"不写具体提示文案，FAIL 时不知道系统该弹什么 |
| 证据要求具体值 | 预期结果中的值必须是**可从系统读取的** | "配置正确"不可读取 |
| 验证点必须可达 | 操作步骤必须**明确验证时机**（保存后？查询后？） | 步骤和验证混在一起，不知道在哪步做断言 |

### 9.2 用例预期结果的编写规则（新增）

**规则一：每条预期必须指明"验证载体"**

| 验证载体 | 写法示例 | 对应断言强度 |
| --- | --- | --- |
| 列表某列 | "列表新增1条，审核状态=未审核" | 强 |
| 列表总条数 | "查询结果共0条，展示'暂无数据'" | 强 |
| 详情页某字段 | "详情页主单金额=999999" | 强 |
| 输入框回显 | "输入框自动展示10.56" | 强 |
| 拦截提示文本 | "出现'最高收费必须严格大于最低收费'类提示" | 中 |
| 弹窗状态 | "弹窗关闭（保存成功）" | 中（需配合列表确认） |
| 下拉选项 | "下拉仅含'快递费''配送费'两项" | 强 |

**规则二：禁止模糊预期词**

| 禁用词 | 为什么禁 | 改成什么 |
| --- | --- | --- |
| "保存成功" | 不指定看哪里确认 | "弹窗关闭+列表新增1条+名称=XX+状态=未审核" |
| "正常展示" | 不指定哪列什么值 | "XX列展示为XX值" |
| "正确处理" | 不可验证 | 写具体处理结果 |
| "符合预期" | 循环论证 | 写预期到底是什么 |
| "拦截" | 不写具体提示 | "出现'XX不能为空'类提示，弹窗保留" |

**规则三：每条用例至少一个强断言预期**

- 用例的预期结果中至少有一条写到"某列=某值"或"总数=N"或"输入框回显=X"的精确程度
- 只有弱预期（"弹窗保留""标题正确"）的用例，需补充强预期或标注为弱验证用例

**规则四：操作步骤中的验证时机标注**

在操作步骤中标注**【验证】**标记，指明在该步骤之后执行断言：
```
操作步骤：1. 新增配置TEST_xxx...；2. 点击【保存】；3.【验证】查询列表，确认新增1条且审核状态=未审核
```

### 9.3 五列格式不变，预期结果列的编写标准升级

现有五列（前置条件/操作步骤/预期结果/判断依据/测试方法）结构不变，但**预期结果列**的编写要求从本标准发布起升级为上述四条规则。
