# 接口测试用例编写标准（通用版）v1.2

> **目的**：让接口测试用例能被执行引擎/AI **确定性**转换为"可执行的请求序列 + 可判定的响应断言"，支持**单接口**与**业务场景链**两类用例，实现高频自动回归、失败自动定位到接口与字段。
> **适用范围**：纳入自动化执行池的所有接口测试用例，含三个来源——人工编写、界面执行流量沉淀、AI 从接口文档生成。
> **定位**：与《AI自动化测试用例编写标准_通用版》（UI 功能用例）**平行的通用层标准**，行业无关、可直接分发；共用同一套领域扩展机制（§9）。UI 用例中的"接口断言（进阶）"只是界面用例内的单点验证，不替代本标准。

---

## 0. 三条总原则

1. **一用例一验证点**：单接口用例只验证一个场景（一条正向或一条反向）；场景链用例只走一条业务路径。
2. **断言必须分层且可判定**：每条用例至少含状态层与一个结构或值断言；"调用成功 / 返回正常"属于无断言写法，一律退回。
3. **数据变量化**：请求参数与断言值中的业务数据一律 `${变量}` 占位，环境相关值（域名、账号、token）一律环境注入，禁止写死。

## 1. 用例整体结构（字段标准）

| 字段 | 必填 | 要求 |
|---|---|---|
| 用例标题 | 是 | 格式：`【接口名-场景】验证点` 或 `【业务场景】路径名` |
| 用例类型 | 是 | `单接口` / `场景链` |
| 接口定义 | 是 | method + path（或接口清单编号引用）；场景链为有序接口列表 |
| 优先级 | 是 | P0 核心链路 / P1 常用功能 / P2 边界扩展 / P3 体验与性能 |
| 前置条件 | 是 | 可准备、可检查：鉴权准备（token 获取方式）、依赖数据（自包含定义） |
| 变量表 | 是 | 请求变量与断言变量（取值方式见 §5） |
| 请求模板 | 是 | headers / query / path 参数 / body，含变量占位 |
| 依赖映射 | 场景链必填 | 上游响应字段 → 下游请求参数的显式映射 |
| 断言集 | 是 | 分层断言列表（§3），逐条可判定 |
| 后置清理 | 否 | 数据回收动作 |
| 来源标记 | 是 | `人工编写` / `UI沉淀` / `AI生成-待审核` |
| 自动化标记 | 是 | `可自动化` / `部分自动化` / `暂不自动化(注明原因)` |

## 2. 请求构造规范（封闭元素）

请求由以下元素构成，写请求时只能使用这些元素（对应 UI 标准的动词表）：

| 元素 | 写法 | 规则 |
|---|---|---|
| 方法与路径 | `POST /api/v1/orders` | 路径不含域名；域名走环境配置 |
| 鉴权头 | `Authorization: ${token}` | token 一律变量或 {env} 注入，**禁止明文**；token 获取方式写进前置条件（登录接口调用链），不依赖 UI 会话 |
| 查询参数 | `?status=${状态}&pageNo=${页码}` | 逐个参数化 |
| 路径参数 | `/orders/${订单ID}` | 变量占位 |
| 请求体 | JSON 模板 + `${变量}` | 字段与接口文档一致；可选字段的省略须在用例中显式说明 |
| 链内传递 | `from: 步骤2.返回.orderId → to: 步骤3.订单ID` | 场景链数据传递必须显式映射，禁止"使用上一步的结果"这类模糊表述 |

**禁止项**：
- ❌ 写死域名、IP、端口、token、账号密码；
- ❌ 依赖界面登录态或人工先造好的数据；
- ❌ 同一请求里既改参数又同时断言多个不相关验证点（拆分用例）。

---

## 3. 响应断言规范（封闭集合，三层）

| 层 | 断言类型 | 允许的写法示例 |
|---|---|---|
| L1 状态断言 | HTTP 状态码 / 业务状态码 | HTTP 200；`code` = `0`（或契约规定的成功码） |
| L2 结构断言 | 字段存在 / 类型 / 必填齐全 | `data.orderId` 存在且为 string；响应含全部必填字段 |
| L3 值断言 | 字段等值 | `data.status` = `CREATED`；`data.customerName` = `${客户名称}` |
| | 数值相等优先 | 金额类字段按**数值比较**（1000.5 = 1000.50），容忍千分位/货币符号等展示格式差异；格式偏离按"待确认问题"提报，不直接判失败 |
| | 集合断言 | `data.list` 共 `1` 条；首条 `status` = `PAID`；全量 `deleted` = `false` |
| | 动态字段规则 | 时间戳、流水号、自增 ID、traceId 等易变字段**只断言存在且格式合法**（如日期格式、非空），**禁止断言具体值** |
| | 空值断言 | 按契约分别断言 `null` / 空串 `""` / `0` / 空数组——四者含义不同不得混写 |
| 数据库断言（进阶） | 落库验证 | 调用后经查询接口或数据通道断言落库字段值；直连数据库须注明通道 |

**禁止的断言写法**（判定为不可自动化，退回）：
- ❌ 调用成功 / 返回正常 / 数据正确（无断言对象）；
- ❌ 无任何断言的冒烟调用（连通性检查须显式标记为"连通性用例"，不占业务用例编号）；
- ❌ 双分支预期："返回错误或空结果"——必须按契约收敛为单一预期；
- ❌ 对动态字段断言具体值（运行必挂）。

## 4. 用例粒度与场景链标准

1. **单接口用例**：一接口一验证点；正向 1~3 条（有效等价类合并），反向按字段重要性 3~8 条（每个无效等价类单独一条）。
2. **场景链用例**：一条业务路径（如 创建→查询→修改→取消），步骤 2~8 步；链内允许数据依赖（经 §2 显式映射），**禁止跨用例依赖**——删掉其他任意用例后本条仍可独立执行。
3. 反向用例单独成条，标题注明预期失败：`【创建订单-反向】验证必填缺失时返回校验错误`。
4. 场景链优先承载业务价值：接口回归的主体应是场景链 + 高风险单接口反向，而非全量单接口穷举。

## 5. 测试数据标准

取值方式与 UI 标准一致，仅四种：`固定值 / 唯一生成 / 上游产出 / 环境注入`。

- 写操作的业务主键（单号、名称）必须"唯一生成"，防污染、防并发冲突。
- **造数通道优先级**：接口造数 > 上游用例产出 > 平台预置数据 > 数据库直插；DB 直插须在用例中标记通道并注明清理方式。
- 禁止"联系开发造数 / 手工先造一批"——确需人工准备则标记 `部分自动化`。
- 清理纪律：场景链在链尾清理；无清理条件的写操作须唯一化数据并登记，由平台定期回收。

## 6. 设计方法矩阵

| 需求要素 | 选用方法 | 用例产出规则 |
|---|---|---|
| 请求字段校验 | 等价类 + 边界值 | 必填缺失、类型非法、长度 0/最大/最大+1、枚举非法值、特殊字符与 SQL 注入载荷——每个无效等价类单独一条；数值型测上下边界及 ±1 |
| 业务规则组合 | 判定表 | 条件组合→响应差异的每条规则列至少 1 条用例 |
| 业务流程 | 场景法（链式） | 每条主路径 1 条链；备选流（取消、超时、中断）各 1 条 |
| 状态流转 | 状态迁移法 | 每个合法迁移 1 条 + 典型非法迁移 1 条（如已取消单据再修改） |
| 幂等与重复 | 重复提交验证 | 同请求连发 2 次：幂等接口断言结果一致且无重复落库；非幂等接口按契约断言第二次的拒绝行为 |
| 鉴权与越权 | 无效凭证 + 越权矩阵 | 无 token / 过期 token / 无效 token 各 1 条；有数据权限的接口测**跨角色 token 越权**（用 A 角色 token 访问 B 角色数据 → 拦截且数据不变）——对应"权限两线覆盖"的 API 线 |
| 并发/时序 | 并发场景设计 | 并发扣减、重复创建、库存竞争——标记"部分自动化"或下沉专用通道 |
| 参数组合查询 | 正交/pairwise | 组合爆炸时按成对组合生成 |
| 历史缺陷高发 | 错误推测 + 缺陷驱动标注 | 历史缺陷对应的请求形态针对性补强，命中条目加【必须验证】标注 |
| 响应性能 | 阈值断言（可选） | 必须量化（如 P95 < 500ms），标记性能层，与功能用例分开调度 |

**数量控制**：单接口 3~10 条为常见区间；枚举穷举与罕见组合不追求 UI 级裁剪，但总量随接口清单增长时优先保证 P0/P1 覆盖，其余按需补充。

## 7. 三类来源与 AI 生成流程

### 7.1 人工编写
按本标准编写，走 §8 评级后入库。

### 7.2 界面执行流量沉淀（UI 采集管道，v1.1 扩写）

**定位**：UI 通道的第一次执行（首测）本身就是接口用例的采集器——首测贵（智能体在线），采集沉淀后回归走接口通道（毫秒级）。

#### 7.2.1 采集机制
UI 首测执行时旁路录制（CDP Network 域 / Playwright request/response 事件 / 平台执行器内置监听），每个请求记录七元组：

`{ method, url, 请求头(鉴权字段脱敏存储), 请求体, 响应体, HTTP状态, 上下文{触发的用例步骤号, 租户, 产品线, 菜单, 时间序} }`

**步骤绑定是采集的价值来源**：只知道"发了什么请求"而没有"哪一步、什么租户下发的"，流量无法还原成用例。

#### 7.2.2 落盘格式
采集记录落 JSONL（或 HAR+扩展字段）；原始报文（HAR/curl）只作素材，不直接入库（v1.0 原则保留）。

#### 7.2.3 采集判定（准入规则）
**锚定原则：该请求的响应是否承载了用例要断言的预期值。** 收集与排除清单：

| 判定 | 对象 | 理由 |
|---|---|---|
| ✅ 收 | 业务数据接口（查询/详情/统计） | 响应即断言来源 |
| ✅ 收 | 业务写接口（保存/提交/审核/删除），含写后读 | 结果可断言 |
| ✅ 收 | 鉴权/越权类（403 判定） | 接口层判定最准 |
| ❌ 不收 | 静态资源（js/css/图片/字体） | 与断言无关 |
| ❌ 不收 | 埋点/日志/监控上报 | 与断言无关 |
| ❌ 不收 | 非本域第三方（地图/CDN 数据/外部分析） | 不可控、无契约 |
| ❌ 不收 | 纯前端行为（前端校验/本地计算/跳转/弹窗开合） | 无接口参与 |
| ❌ 不收 | 中间态请求（轮询/防抖重复/验证码/心跳） | 非稳定契约 |
| ❌ 不收 | 二进制流（文件上传下载） | 难以值断言（专门设计除外） |
| ❌ 不收 | 一次性凭证/临时 token 类 | 不可重现 |

**判定捷径（按断言类型反推）**：数据正确性（金额/数量/状态/列表）→必收；操作结果（含写后读）→收；文案/提示语→不收（走 UI 通道）；布局/控件状态/交互→不收；权限越权→收。

#### 7.2.4 原料清洗与转换规则
1. **参数化**：录制的具体业务值改写为 `${变量}`（固定值/唯一生成/上游产出/环境注入四选一，按 §5）；
2. **环境值注入**：域名、token、账号一律 `{env}` 注入，录制报文中的真实 token 只用于标注获取方式（登录链），不落盘明文；
3. **唯一化改写**：单号/名称类改"唯一生成"模板（防污染）；
4. **调用序列还原**：同一步骤内的并发、重试、重复请求去重，按时间序还原业务链；跨步骤的依赖写 §2 显式映射；
5. **响应基准提取**：从响应中提取候选断言值与断言层级（§3），标 `候选基准`。

#### 7.2.5 首录值 ≠ 正确值（基准确认纪律）
**录到的响应是"系统当时的值"，不一定是"正确的值"**——测试环境数据本身可能有错，照抄首录值会把错误固化成断言。规则：
- 首录值只作**候选基准**；
- 金额/状态/口径类断言值必须回溯**断言基线库（BL-xxx）或拍板记录**确认后方可定稿；
- 确认不了的标 `待拍板`，**不得进入执行池**（与 UI 用例"疑问前置"纪律同构）。

#### 7.2.6 回放验证与字段稳定性 diff（v1.0 原则保留）
- **回放验证**：独立取 token、脱离 UI 重放通过，才可入库；
- **字段稳定性 diff**：同一链路执行两遍，响应中取值变化的字段自动标记为动态字段，断言降级为"存在且格式合法"。

#### 7.2.7 入库与溯源
- 来源标记 `UI沉淀`，并附**血缘**：`{源UI用例编号, 源步骤号, 菜单, 租户, 采集时间, 采集执行ID}`；
- **生命周期联动**：源 UI 用例的断言步骤被删除/改版 → 对应接口用例自动标 `失效待复审`；口径拍板更新（BL 条目变更）→ 关联接口断言同步更新并留痕。接口用例回归失败时，凭血缘判定"修用例还是修接口用例还是报缺陷"。

### 7.3 AI 从接口文档生成
四步流程（与 UI 标准同构）：**文档解析**（OpenAPI/Swagger 提取接口清单、参数约束、响应结构）→ **方法匹配**（按 §6 矩阵）→ **生成**（请求模板+断言集+变量化）→ **回放验证 + 人工审核**（来源标记 `AI生成-待审核`，覆盖自检表随附，审核通过才进执行池）。

**覆盖自检表**（AI 必须随草稿输出）：`接口 × 方法 × 覆盖项（等价类/边界/规则列/迁移/幂等/越权） × 用例编号`——审核人据此核对漏项。

## 8. 可自动化性评级（存量摸底/验收用）

| 维度 | 检查项 | 不满足时的整改 |
|---|---|---|
| A 结构完整 | 有接口定义、请求模板、分层断言 | 补齐结构 |
| B 请求可构造 | 参数变量化、鉴权环境注入、无写死环境值 | 变量化改造 |
| C 断言可判定 | 断言可映射 §3 断言集、无动态字段断值、无双分支 | 补/改断言 |
| D 数据可构造可清理 | 四种取值方式之一、写操作唯一化、有清理或登记 | 补数据方案 |

评级补充判定：
- Postman 集合 / curl 脚本 / HAR 报文导入 → 视为**素材**，须提炼为本标准格式再评级入库；
- 场景链缺失依赖映射的 → 补 §2 映射表后评级。

验收目标：核心接口（P0/P1 场景链涉及）正向+反向+越权覆盖齐全，可自动化率 ≥ 80%。

## 9. 领域扩展机制与姊妹标准关系

- **共用扩展机制**：与《AI自动化测试用例编写标准_通用版》§8 完全一致——A 类行为断言基线库（接口类基线：业务码枚举、金额格式、空与 0 口径、分页约定等，引用 BL 编号）、B 类领域设计规则库；用例携带领域元数据（系统/租户/产品线）匹配基线。
- **与 UI 标准的衔接**：UI 用例执行沉淀接口用例时，沉淀产物按**本标准**落格式与评级；UI 标准的"接口断言（进阶）"仅是界面用例内的单点接口验证。
- **与执行平台分层调度**：接口用例每次部署后/每日执行（分钟级），UI 用例按日/发版执行——两份标准对应两条用例产线，共用缺陷闭环与确认机制。

## 10. 附：编译后内部交换格式（平台内部使用）

```yaml
case_id: API-2026-000001
case_type: scenario_chain        # single_api | scenario_chain
source: ui_captured              # manual | ui_captured | ai_generated
domain: { system: 示例系统, tenant: T1, product_line: 示例线 }
variables:
  订单号: { gen: "DD${ts:yyyyMMddHHmmss}", unique: true }
  token: { env: test_user_token }
steps:
  - step: 1
    request: { method: POST, path: /api/v1/orders,
      headers: { Authorization: "${token}" },
      body: { customerName: "${客户名称}", remark: "接口回归" } }
    asserts:
      - { layer: L1, type: biz_code_equal, value: 0 }
      - { layer: L2, type: field_exists, path: data.orderId }
    exports: { 订单ID: data.orderId }
  - step: 2
    request: { method: GET, path: /api/v1/orders/${订单ID} }
    asserts:
      - { layer: L3, type: field_equal, path: data.status, value: CREATED }
      - { layer: L3, type: numeric_equal, path: data.amount, value: "${预期金额}" }
cleanup:
  - { request: { method: POST, path: /api/v1/orders/${订单ID}/cancel } }
```
