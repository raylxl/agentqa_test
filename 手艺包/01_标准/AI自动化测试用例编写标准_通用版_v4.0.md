# AI 自动化测试用例编写标准（通用版）v4.0

> **目的**：让功能测试用例能被 AI 编译器**确定性**转换为"可执行动作序列 + 可判定断言"，实现自动执行、自动比对预期、不一致自动建缺陷。
> **适用范围**：纳入 AI 自动化执行池的所有 UI 功能用例，含人工编写的存量用例与 AI 生成的用例草稿；行业无关，可直接分发给任何测试团队。
> **两层架构**：本文件是**通用层**（方法论与格式标准，不含任何特定系统的专属数据）；行业/系统专属的"行为断言基线、设计规则、检查门禁"通过 **§8 领域扩展机制**以独立文件挂载。正文与扩展分离，通用层稳定少变、领域层持续吸收业务数据更新。
> **姊妹标准**：接口测试用例按《接口测试用例编写标准_通用版》执行（同为通用层，共用领域扩展机制）；本标准聚焦 UI 功能用例，其"接口断言（进阶）"不替代接口用例标准。

---

## 0. 三条总原则

1. **一步 = 一个操作 + 一条可判定预期**。AI 按步骤编译动作、按预期生成断言，缺任何一半该步骤就无法执行或无法判定。
2. **元素指代必须用页面可见文案**。AI 靠页面文字定位元素，用例里必须出现按钮文字、字段标签、列名、菜单名。
3. **预期必须可判定**。"页面正常 / 显示正确 / 功能正常"属于不可判定写法，一律退回重写。

## 0.5 测试角色自检（每次任务第 0 步）

任何测试任务（需求澄清 / 用例设计 / 执行 / 反馈）开工前，先完成一次角色自检，再进入标准流程。

**一句话定位**：在正确的时间，用最少的成本，给出最高置信度的质量判断——并在缺陷发生之前阻止它。测试交付的不是"跑完用例的任务"，而是"这个功能能不能上线的判断"。

**六层能力姿态**：

1. **全视角**：业务（解决用户问题吗）/ 用户（用得顺手吗）/ 技术（实现稳定吗）/ 视觉（界面专业吗）/ 数据（正确且安全吗）五视角缺一不可，不画线说"这不是我的事"；
2. **缺陷预防前置**：在需求澄清阶段就挑战模糊与矛盾；在用例设计阶段用矩阵**消灭整类问题**，而不是逐条试错；
3. **风险驱动**：按 业务影响 × 发发生概率 排优先级；知道什么可以不测（风险低于测试成本）；每轮结束输出**置信度判断**（"我认为可以/不可以进入下一阶段，依据是……"），不只报通过数；
4. **全谱系**：功能 / UI 样式 / 性能 / 兼容 / 安全 / 可靠性 / 可用性 / 可访问性——接任务先逐维确认测不测；无明确要求的维度**主动给出建议**，不默认不做；
5. **自动化与工具链**：自己建工具、写脚本、搭流水线，让重复的事自动化、让测试又快又稳；
6. **元质量**：每个漏掉的缺陷反推"为什么我没发现它"，把教训回写进标准——从"我测了很多"到"我测的方法越来越好"。

**自检产出**：本任务的"全谱系清单"（测哪几维、不测哪几维、理由）与置信度承诺，记入任务 Brief 首行。

## 1. 用例整体结构（字段标准）

| 字段 | 必填 | 要求 |
|---|---|---|
| 用例标题 | 是 | 格式：`【模块-子功能】验证点描述`，一句话说清验证什么 |
| 模块/需求/迭代关联 | 是 | 在用例管理系统中关联，缺陷建单时自动带上 |
| 优先级 | 是 | P0 核心链路（冒烟）/ P1 核心功能 / P2 扩展、边界、性能 / P3 体验优化 |
| 前置条件 | 是 | 编号列表，必须可准备、可检查（见 §4） |
| 测试数据 | 是 | 变量表（见 §5）；无特殊数据可写"无" |
| 步骤 | 是 | 有序步骤列表，每步含操作+预期（见 §2） |
| 后置清理 | 否 | 需要回收数据时写明清理动作 |
| 自动化标记 | 是 | `可自动化` / `部分自动化(注明人工步骤)` / `暂不自动化(注明原因)` |

## 2. 步骤编写标准（核心）

每一步骤由两部分组成，分别填入"步骤描述"和"预期结果"：
- **操作（Action）**：一个原子动作，动词开头，只做一件事。
- **预期（Expected）**：本步操作完成后可观察、可判定的结果。

### 2.1 操作动词表（封闭集合）

AI 编译器只认以下动词类别，写操作时必须从表中选用：

| 类别 | 允许的写法示例 |
|---|---|
| 导航 | 打开菜单「订单管理-创建订单」；访问页面「/order/create」 |
| 输入 | 在「订单号」输入 `${订单号}`；清空「备注」；在「附件」上传文件 `${附件路径}` |
| 点击 | 点击「保存」；双击表格行；右键「列头」；悬停「更多」 |
| 选择 | 在「客户」下拉选择 `${客户名称}`；勾选「第一条记录」；切换到页签「明细」；单选「加急」 |
| 表格 | 在表格第 `${N}` 行点击「操作-编辑」；在「状态」列筛选「待处理」 |
| 弹窗 | 点击「确认」接受弹窗；关闭提示「操作成功」 |
| 等待 | 等待「保存成功」提示出现（**只允许等元素/提示，禁止写"等待 N 秒"这类时间等待**） |
| 校验 | "查看"/"验证"开头的纯断言步骤（无页面操作） |

**写法规则：**
- 复合动作必须拆开：「填写所有信息并点击保存」→ 拆为输入步骤 + 点击步骤。
- 元素指代禁止"那个按钮/上面的框"，必须写页面可见文案。
- 数据一律用变量 `${变量名}` 占位，禁止在步骤里写死具体值。

### 2.2 预期断言表（封闭集合）

预期必须能映射到以下断言类型之一：

| 断言类型 | 允许的写法示例 |
|---|---|
| 元素断言 | 页面出现「创建订单」表单；「删除」按钮消失 |
| 文本断言 | 「客户」字段显示 `${客户名称}`；提示文案显示「保存成功」 |
| 列表断言 | 列表共 `1` 条；第一行「状态」列显示「待处理」 |
| 状态断言 | 「保存」按钮置灰不可点击；单据状态变为「已创建」 |
| 弹窗断言 | 出现确认弹窗，内容包含「确认提交」 |
| 接口断言（进阶） | 「创建订单」请求返回成功，且返回的 `status` 字段为 `CREATED` |

**提示文案断言分级**（通用规则）：
- **固定文案**（需求原文明确规定的）→ 逐字断言；
- **无统一标准的提示**（各需求/菜单可能不同）→ 只断言"提示出现 + 操作被拦截或完成 + 数据状态变化"，**不逐字断言文案**；实际文案由执行层记录为"待确认文案"反馈人工确认。

**禁止的预期写法**（一律判定为不可自动化，退回）：
- ❌ 页面正常 / 显示正确 / 功能正常 / 数据正确
- ❌ 模糊量词：「显示了很多记录」「速度很快」
- ❌ 不可观察的内部行为：「数据库写入成功」（除非改写为接口断言）
- ❌ 双分支/条件式预期：「提示或置空」「根据业务而定」——进自动化池前必须收敛为单一预期

涉及**系统固有行为**（输入框越界的处理方式、拦截方式、批量操作策略等）的预期，直接引用领域扩展文件（行为断言基线库）中的既有口径，不得自创；无基线可引时先补基线再写用例。

## 3. 用例粒度标准

1. 一条用例只验证**一个场景一个验证点**（一条正向路径 或 一条反向路径），不混用。
2. 步骤数建议 3~10 步；超过 10 步考虑拆分为多条用例。
3. 一条用例必须是一个**可独立建缺陷的单元**：任意步骤失败都能对应到一个明确的缺陷描述。
4. 反向用例单独成条，标题注明预期失败：`【订单管理-创建】验证必填缺失时保存被拦截`。

---

## 4. 前置条件标准

- 只写**可由系统准备或可自动检查**的条件，每条可执行：
  - ✅ 已登录被测系统测试环境，当前租户为「测试租户A」
  - ✅ 存在状态为「待处理」的订单 `${订单号}`（由前置用例创建或平台造数）
- ❌ 不允许："联系开发准备数据""手动造一批单据"——若确实需要，标记该用例 `部分自动化` 并注明人工步骤。
- 每条用例**自包含**：前置数据/状态由本用例自行定义，禁止"上述/同上/前述"等跨用例引用；判定法：删掉其他任意用例后，本条仍能独立构造前置并执行。
- 前置数据建议链式复用：上游用例的产出变量作为下游用例的前置（平台按执行顺序传递）。

## 5. 测试数据标准

变量表字段：`变量名 | 取值方式 | 示例/规则`。取值方式只有四种：

| 取值方式 | 含义 | 示例 |
|---|---|---|
| 固定值 | 每次执行相同 | 客户名称 = 测试客户A |
| 唯一生成 | 执行时自动加时间戳后缀防冲突 | 订单号 = `DD${yyyyMMddHHmmss}` |
| 前置产出 | 由本用例前序步骤或上游用例返回 | 订单ID = 步骤2返回的单号 |
| 环境注入 | 登录账号、租户等由平台环境配置注入，不写在用例里 | 登录账号 = {env.test_user} |

要求：
- 涉及**写操作**的业务主键（单号、名称）必须用"唯一生成"，避免污染和并发冲突。
- 账号、密码、租户等环境信息一律环境注入，禁止明文写入用例。
- 有清理要求的写用例补充后置清理步骤（或标记由平台定期清理测试数据）。
- 金额类数据断言以**数值相等**优先判定，不因千分位/货币符号等展示格式差异直接判失败；格式偏离按"待确认问题"提报（展示格式标准由领域扩展文件定义）。

## 6. AI 生成用例：设计方法与流程

### 6.1 生成流程（四步）

1. **需求解析**：AI 从需求文档提取《需求要素清单》，固定结构输出：功能点列表 / 输入字段及约束（类型、长度、必填、枚举取值、数值范围、默认值）/ 业务规则（"条件→结果"的 if-then 形式）/ 业务流程与状态流转 / 角色与权限。解析结果随用例草稿一起输出，供审核人核对需求无遗漏、无理解偏差。
2. **方法匹配**：按 6.2 矩阵为每个功能点选择设计方法，可多选叠加；领域专项方法由领域设计规则库扩展。
3. **用例生成**：按所选方法的产出规则和本标准格式逐条生成。
4. **覆盖自检**：AI 随附《覆盖自检表》（6.4），列明每个功能点用了哪些方法、覆盖了哪些等价类/边界/规则列/迁移路径。

### 6.2 通用设计方法矩阵

| 需求要素特征 | 选用方法 | 用例产出规则 |
|---|---|---|
| 输入字段/表单校验 | 等价类划分 + 边界值分析 | 有效等价类尽量合并；**每个无效等价类单独一条**；数值测上/下边界及±1，长度测 0/最大/最大+1，枚举逐取值；字段校验必须"录入→保存→观察结果"，禁止纯展示观察 |
| 业务规则组合 | 判定表法（条件间有约束时先用因果图梳理） | 每条规则正向（满足）+反向（违反）各≥1 条；判定表**每条规则列至少 1 条用例**；组合过多先精简再转正交 |
| 端到端业务流程 | 场景法 | 基本流 1 条；每个备选流（取消、驳回、超时、中断恢复）至少 1 条 |
| 状态流转 | 状态迁移法 + 多状态字段组合穷举 | 每个合法迁移 1 条 + 典型非法迁移 1 条；多个状态字段（如审核状态×生效状态）按组合矩阵逐格覆盖 |
| 角色/权限 | 权限矩阵法（角色 × 功能 × 数据范围），**两线覆盖** | 前端行为线：按钮显隐/拦截表现 + 数据范围断言（本级及下级等）；接口层拦截线：绕过前端直调接口被拦、数据不变——两线各至少 1 条 |
| 字段联动 | 联动测试法 | 每种联动：正向联动 + 切换清空 + 边界 |
| 多参数组合查询/配置 | 正交实验法（成对组合 pairwise） | 全组合爆炸时按两两组合生成，并说明正交表选用依据 |
| 查询条件 | 三态覆盖法 | 每个条件：正向命中 + 模糊匹配（如有）+ 反向不存在 + 可边界则边界 |
| 历史缺陷高发/易错点 | 错误推测法 + 缺陷驱动标注 | 将缺陷管理系统历史缺陷喂给 AI 针对性补强；命中的用例名称前加【必须验证】/【重点关注】/【回归检查】标注，并与优先级建立映射 |
| 并发/时序（扣减、重复提交、幂等） | 并发场景设计 | 标记"部分自动化"，或下沉到接口层执行 |

### 6.3 数量与优先级控制（防用例爆炸）

- 单个功能点 UI 用例常见区间 **5~15 条**；超出时 AI 必须说明原因，或建议将枚举穷举、罕见组合**下沉到接口层**（与"UI 执行沉淀接口用例"的分层策略衔接）。
- 优先级映射：P0 = 场景法基本流 + 判定表主规则 + 主边界；P1 = 备选流 + 其余边界 + 权限；P2 = 罕见组合与错误推测补充；P3（体验优化类）默认不进 UI 自动化池。
- "需求级总量参考"（如 50~400+ 条）与"单功能点 5~15 条"不冲突：前者是整需求（含全部功能点）的总量口径。
- 标注与优先级等式（如 P0 =【必须验证】）生成后须复核成立。

### 6.4 覆盖自检表（AI 必须随用例草稿输出）

| 功能点 | 选用方法 | 覆盖项（等价类/边界值/规则列/迁移路径） | 用例编号 |
|---|---|---|---|

审核人按此表核对三件事：字段有没有漏做等价类、判定表规则列全不全、备选流和非法状态迁移有没有遗漏。

### 6.5 附加要求

1. **来源标记**：AI 生成的用例标记 `AI生成-待审核`，人工审核通过后才进入执行池，审核动作记录留痕。
2. **同标合规**：AI 生成用例与人工用例执行同一套标准（动词表、断言表、变量规范），不符合即视为生成失败自动重生成，不带病入库。
3. **需求歧义不擅自闭合**：遇系统兜底未定义、边界预期不明等，登记"待确认开放项"，用例只写场景框架+风险标注，预期待回填——不得替产品做假设预期。
4. **审核检查清单**（人工审核时逐项确认）：
   - [ ] 需求要素清单无遗漏、无理解偏差（功能点/字段/规则/流程/角色）
   - [ ] 方法选择合理，覆盖自检表与实际用例一致
   - [ ] 步骤在被测页面上真实可操作（菜单/按钮确实存在）
   - [ ] 预期与需求描述一致，且可判定（含：双分支已收敛、执行文本零内部代号）
   - [ ] 测试数据可构造、可清理，粒度合规（一用例一验证点）
   - [ ] 检查独立于生成：覆盖核对不复用生成时的取舍假设
   - [ ] 覆盖映射表每行指向具体用例编号，无"沿用vX/同模式/共通不重复设计"充当覆盖证据

### 6.6 生成与检查分离（双门禁）

生成方不得自证质量。两道门禁各配独立检查方：

- **设计域门禁（生成 vs 质疑）**：AI 生成用例后，由**独立于生成过程的质疑方**复核——不采信生成方的自述，按设计方法正本**独立重推导**、逐格对照"规划矩阵 vs 实际产出"、对可疑点做对抗性提问（负向三问：漏了什么 / 什么情况下会错 / 哪个假设未经验证）。问题回流生成方修复，循环至零新发现收敛，由**质疑方签发**完成证书。
- **执行域门禁（生产 vs 质检）**：执行 / 回写 / 报告的生产方完成后，由独立质检方核验**客观锚点**（回写是否真实落盘、数字是否对账、抽样重放断言是否成立）。生产方口头或自述"已完成"不构成完成证据。

原因：同一过程既当运动员又当裁判时，会系统性放大自己的取舍假设；分离后，生成时的假设必须经受独立重推导才能存活。

## 7. 可自动化性评级（存量用例摸底/验收用）

对存量用例按四个维度打分：

| 维度 | 检查项 | 不满足时的整改 |
|---|---|---|
| A 结构完整 | 有前置条件、步骤、预期分层 | 补齐结构 |
| B 动词规范 | 每步操作可映射动词表 | 改写步骤描述 |
| C 预期可判定 | 每步预期可映射断言表 | 补/改预期描述 |
| D 数据可构造 | 变量四种取值方式之一，写操作有唯一性 | 补测试数据方案 |

评级结论：A/B/C/D 全满足 → 可直接自动化；缺 C → 补预期（通常占比最高）；缺 B → 改写步骤；缺 D → 需数据方案（部分转"部分自动化"）。
验收目标：核心模块（P0/P1）存量用例可自动化率 ≥ 80%。

## 8. 领域扩展机制（通用层与专属数据的耦合方式）

本标准正文不含任何特定系统的数据；所有行业/系统专属内容以**领域扩展文件**挂载，本节定义挂载与更新规则。

### 8.1 扩展文件两类

| 类型 | 内容 | 回答的问题 | 形态 |
|---|---|---|---|
| **A 行为断言基线库** | 系统实测行为事实（控件行为、拦截方式、批量策略、业务计算规则、枚举全集、权限矩阵） | "预期怎么写才对" | 条目制：编号 + 基线 + 断言写法 + 适用范围 + 来源指针 + 状态 |
| **B 领域设计规则库** | 业务化设计方法、专项设计规则（如按钮/权限/记录类功能的设计法）、生成后检查门禁、口径裁决记录 | "用例怎么设计才全" | 规则制：设计规则 + 用例产出规则 + 源文件指针 |

### 8.2 挂载与匹配

- 每份领域文件在文件头声明**适用范围**：系统 / 租户 / 产品线 / 功能域。
- 用例与执行计划携带**领域元数据**（系统、租户、产品线等），断言与设计规则按维度匹配领域条目——同一条通用用例在不同领域维度下可命中不同基线口径（例：同一匹配场景在两个租户下的预期相反，由各自基线条目承载）。
- 通用层引用领域文件用**编号**（如 RULE-017、DR-03），不复制正文，保证单一事实源。

### 8.3 扩展文件准入与生命周期

- **准入门槛**：新条目必须有来源指针（源标准文件章节、需求原文、实测记录、或负责人确认记录），无法溯源不入库。
- **条目生命周期**：待确认 →（实测/拍板）→ 实测确认 →（口径变化）→ 修订（原文在版本记录留痕，不删除）；编号只增不回收。
- **状态标记**：实测确认 / 文案待对齐 / 待实测收敛 / 口径演进 / PENDING（代码与定论不符时按定论写预期、实测后提缺陷）。

### 8.4 更新融合协议（领域数据更新的固定流程）

当上游源标准文件/需求沉淀文件更新时：
1. **diff 新旧源**，定位新增"错误→正确"对照、新固化章节、新口径裁决；
2. **增量提炼**：全新内容→按模板追加新条目；口径变化→修订原条目并留痕；被推翻的旧口径不移除、只留痕；
3. **只改领域文件，不改通用标准**——通用层仅在方法论本身演进时才升版（如动词表/断言表扩充）；
4. 每次融合在领域文件版本记录登记，保证任意时点可回答"这条口径从哪来、何时定的"。

### 8.5 标准定位序与口径归属（防止套错标准）

- **定位序**（每个新需求/新系统开工时走一遍）：
  1. **判领域**：被测对象属于哪个领域/系统？该领域有没有挂载的领域扩展文件（A/B 类）？
  2. **查本地口径**：项目内有没有已沉淀的领域标准/需求理解说明？
  3. **列适用集**：把"通用层 + 领域扩展 + 项目本地口径"的现行版本列全，作为本任务的标准清单，记入 Brief 首行；
  4. **判不准就问，禁默认套用**：某条口径拿不准属于通用、领域还是项目本地，停下来问负责人，不得凭感觉套用。
- **口径唯一归属**：每条规则只能有一个正本归属层（通用 / 领域扩展 / 项目本地），一处正本、他处只放指针；跨层复制正文＝口径分叉的开始。

## 9. 合格示例与反例

### 合格示例（通用工单场景）

> **用例标题**：【工单管理-创建】验证必填信息完整时创建工单成功
> **优先级**：P0　**自动化标记**：可自动化
> **前置条件**：
> 1. 已登录被测系统测试环境，当前租户为「测试租户A」
> 2. 存在可用客户档案 `${客户名称}`
> **测试数据**：
>
> | 变量名 | 取值方式 | 示例/规则 |
> |---|---|---|
> | 工单号 | 唯一生成 | `GD${yyyyMMddHHmmss}` |
> | 客户名称 | 固定值 | 测试客户A |
> | 备注 | 固定值 | AI自动化回归 |
>
> **步骤**：
>
> | # | 操作 | 预期 |
> |---|---|---|
> | 1 | 打开菜单「工单管理-创建工单」 | 页面出现「创建工单」表单 |
> | 2 | 在「客户」下拉选择 `${客户名称}` | 「客户」字段显示 `${客户名称}` |
> | 3 | 在「工单号」输入 `${工单号}` | 输入框内容为 `${工单号}` |
> | 4 | 点击「保存」 | 出现提示「保存成功」 |
> | 5 | 切换到页签「工单列表」 | 列表第一行「工单号」列显示 `${工单号}`，「状态」列显示「待处理」 |
>
> **后置清理**：作废工单 `${工单号}`

### 反例对照（同场景的不合格写法）

> ❌ 标题：测试创建工单
> ❌ 步骤：1. 输入所有必填信息，点击保存
> ❌ 预期：页面正常，保存成功
>
> 不合格原因：复合动作未拆分；"所有必填信息"无变量定义；"页面正常"不可判定；无元素文案无法定位。

## 10. 附：编译后的内部交换格式（平台内部使用）

人工/AI 用例按本标准编写，平台编译器将其转换为如下结构化格式缓存执行（用例版本变更时重编译）。此格式仅供平台内部与排查使用，**用例作者无需手写**：

```yaml
case_id: PM-2026-000123
case_version: 3
title: 【工单管理-创建】验证必填信息完整时创建工单成功
priority: P0
domain: { system: 示例系统, tenant: 测试租户A, product_line: 示例线 }   # 领域元数据：用于匹配领域扩展条目
preconditions:
  - type: login_env
    tenant: 测试租户A
  - type: data_exists
    entity: 客户档案
    where: { name: "${客户名称}" }
variables:
  工单号: { gen: "GD${ts:yyyyMMddHHmmss}", unique: true }
  客户名称: { const: 测试客户A }
steps:
  - action: navigate_menu
    target: { menu: [工单管理, 创建工单] }
    assert: { type: element_visible, target: 创建工单表单 }
  - action: select
    target: { label: 客户 }
    value: "${客户名称}"
    assert: { type: text_equal, target: 客户, value: "${客户名称}" }
  - action: click
    target: { button: 保存 }
    assert: { type: toast_contains, value: 保存成功 }
cleanup:
  - action: api_call
    desc: 作废工单 ${工单号}
```

## 11. 执行就绪度尺（设计期出口的机检清单）

设计完成 ≠ 执行就绪。用例册交付执行前按下表逐条机检（脚本或人工），违例当轮修：

| # | 检查项 | 判据 |
|---|---|---|
| 11.1 | 操作动词白名单 | 步骤动词限于 §2.1 动词表；"验证/检查/确认"类心理动词禁单独成步（须落到具体操作+断言） |
| 11.2 | 控件指代格式 | 被操作控件一律「页面可见文案」；禁"该按钮/上述输入框"等相对指代 |
| 11.3 | 输入值具体 | 禁"合法数据/正确格式/若干"；须确切值或 ${变量}＋取值来源 |
| 11.4 | 断言可判定 | 预期必含可观测信号（文案/数值/状态/行数/响应字段/元素存在性）；"页面正常/显示正确/功能正常"＝黑名单 |

| 11.6 | 数值禁模糊量词 | 禁"大约/左右"；金额/数量写精确值或区间 |

## 12. 执行结果四态与执行纪律

### 12.1 结果四态（封闭集合）

| 状态 | 含义 | 判定 |
|---|---|---|
| PASS | 全部断言通过 | 断言逐条成立 |
| FAIL | 任一断言不成立 | 附截图/报文/差异证据 |
| NOT_EXECUTED | 未到达验证点 | 写明原因（前置失败/环境不可用等），禁与 FAIL 混算 |
| BLOCKED | 被环境/依赖阻断 | 写明阻断原因与处置；修复后复跑 |

无断言的步骤/用例禁标 PASS——"什么都不验证、必过"的用例是无效用例。

### 12.2 执行纪律（防"跑了很多但没跑完"）

1. **批量优先**：先建批量执行器再谈单条调试，禁逐条人工驱动替代批量执行；
2. **超时下一条**：单条卡住超过约定时限（如 5 分钟）即标 BLOCKED 跑下一条，禁停下来调试工具；
3. **覆盖度实时可见**：执行过程中随时能报出"已执行/总数/通过率"，禁"跑完才知道跑了多少"；
4. **一份报告**：全部批次并入一份执行报告，禁按批次出版多份；
5. **结论限定在覆盖内**：只对实际执行的用例下结论，禁用"全部通过"概括未执行部分；
6. **失败复测轮**（2026-11-17 立）：批量执行结束后对本轮全部 FAIL 条目自动复测一轮（换通道交叉优先：UI 首败走接口验数据态、接口首败走 UI 验展示态）；复测通过且首败无系统错误消息原文＝PASS(复测) 全披露（首败记录保留），首败含错误原文＝挂起待复验转人工禁自动翻案，仍失败＝FAIL 两轮证据并列（复现率偶发 1/2·必现 2/2）——环境/偶发误报在呈报前自动消化，判定语义见《测试执行结果判定标准》§5.1。

### 12.3 分层执行模式（成本递减）

AI 首跑（覆盖广、单条成本高）→ PASS 条目沉淀为执行脚本（一次性转化）→ 后续回归走脚本（近零边际成本）→ 脚本失败回流 AI 定性。新用例永远先走 AI 首跑，成熟用例逐步沉入脚本层。

## 13. 执行出口尺（全部满足才可出执行报告终版）

- **P0 用例通过率 = 100%**（任一失败禁止出口，回缺陷流程）；
- **P1 用例通过率 ≥ 95%**（非阻塞 Fail 逐条说明）；
- **P2/P3 未执行项**：每条必须有执行集、风险理由和处置结论，禁用"低优先级"代替原因；
- **需求覆盖率 = 100%**（对照需求要素清单逐项对账）；
- **风险覆盖率 = 100%**：每个高风险项必须有高优先级用例、或经负责人确认的不测/观察处置；
- **Skip 零遗留**（有则逐条说明并登记待复验；明确标记的人工执行与已失效条除外、逐条列出）；
- **环境类误报清零**（隔离或修复后复跑受影响用例）。

出口不满足时：P0 失败→退回修复；P1 失败率超限→分析后裁定退回或升级；覆盖不足→补用例重执行；Blocked 大量→修环境重跑受影响用例。

## 14. 执行反馈闭环：分流与四源回写

### 14.1 不一致分流（三选一）

实现 ≠ 预期时，先查该条用例的判断依据出处，再分流：

| 分流 | 判定 | 动作 | 用例 |
|---|---|---|---|
| ① 用例对、实现错 | 断言依据＝需求原文/已确认口径 | 建缺陷单（描述引用用例编号+依据出处） | 不动 |
| ② 实现为准、用例口径旧 | 开发确认实现口径/代码实证 | 按 §14.2 呈报，负责人确认后修用例 | 修/补/删 |
| ③ 需求本身变 | 口径变化超出原确认范围 | 回需求澄清环节重新确认，评估影响面后批量修 | 批量修 |

两可时呈报、不擅自分流。

### 14.2 呈报五段式（一次一事）

1. **现象**：环境 + 用例编号 + 步骤号 + 预期 vs 实际（截图/报文佐证）；
2. **用例原文与出处**：该条判断依据内容 + 口径出处；
3. **系统实际表现**：可观测事实，不掺推断；
4. **分流初判**：三选一 + 理由；
5. **处置请求**：修用例（附建议改法）/ 建缺陷 / 回澄清——负责人文字回复即定夺。

### 14.3 四源回写盘点（每轮执行收尾必做）

执行收尾时，执行方**主动**盘点四类变化并呈报"需不需要改"——不等负责人发现、不等指令；负责人只做定夺，不做发起。回写一律在定夺后执行（冻结纪律）。

| 源 | 定义 | 承载形式 | 关键要求 |
|---|---|---|---|
| **SYS** 系统与用例不符 | 执行不一致项 + 缺陷定案与原预期冲突 | 修正章（TC-SYS 前缀） | 必须挂老用例编号；断言按系统定案行为写 |
| **DEF** 缺陷数据新增 | 缺陷平台本模块全量单引入的、原册没有的场景 | 新增章（TC-DEF 前缀） | 拉单比对，来源＝缺陷单号 |
| **IMP** 实现行为固化 | 需求未定义但已落定的实测行为 | 行为契约章（TC-IMP 前缀） | 标"需求未定义·实现行为固化"；同构场景**逐控件实测、禁推定**；断言终判以提交/落库结果为准，控件显示不作唯一判据 |
| **CHG** 需求变更 | 需求中途变更/补充（全新增 or 推翻原预期） | 变更章（TC-CHG 前缀） | 标〔来源：需求变更…〕；推翻原条须挂老用例编号 |

**回写纪律**：原用例正文不动，变化进增量章；被推翻的原条打**失效标识**（标题划线 + 〔已失效〕+ 替代指针指向新条），全量执行遇失效条自动跳过、以增量章对应条执行；每次回写后重过结构门禁。候选必须按完整用例格式逐条展示供确认——一句话清单视为无效呈报。
