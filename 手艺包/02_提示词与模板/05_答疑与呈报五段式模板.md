# 答疑与呈报五段式模板 v1.0

> 两个"五段式"：一个用于**需求澄清提问**（设计前），一个用于**执行不一致呈报**（执行后）。共同纪律：**一次一事、对话内文字定夺、逐条编号、只增不覆盖**。

---

## 一、需求答疑提问五段式（一次一问，禁一次抛一串）

拿需求原文逐段扫描（结构/流程/权限/边界/架构五个面），有疑问就按下面五段提一条：

1. **疑问**：一句话说清疑问点（Q1、Q2…连续编号）；
2. **原文引用**：需求文档原句粘贴（含章节号），证明疑问有出处；
3. **解读并列**：列出所有合理解读（≥2 种），不预设立场；
4. **候选方案**：每种解读对应的处理方案，附**建议项**及理由；
5. **对用例设计的影响**：选不同解读会导致哪些用例/断言不同——让定夺人知道这个问题的分量。

**纪律**：
- 一次只问一条，文字回复即定夺，回写《口径确认记录》（04 模板§三）；
- 定夺前不用例落笔：所有疑问闭环（零待定）才进设计——**尾巴留到设计期=整批返工**；
- 问句型检查项按系统事实作答，禁把问句误读为肯定式；
- 需求原文提到 ≠ 必须出用例：先问"这是要测的点还是背景说明"。

## 二、执行不一致呈报五段式（一次一事）

执行中发现"实现 ≠ 预期"，按五段呈报，负责人文字回复即定夺：

1. **现象**：环境 + 用例编号 + 步骤号 + 预期 vs 实际（截图/报文佐证）；
2. **用例原文与出处**：该条判断依据格内容 + 口径出处（需求原文/确认记录编号/基线库编号）；
3. **系统实际表现**：可观测事实，不掺推断；
4. **分流初判**：三选一 + 理由——① 用例对、实现错（建议建缺陷单）；② 实现为准、用例口径旧（建议修用例，附建议改法）；③ 需求本身变（建议回澄清重新定夺）；
5. **处置请求**：明确要对方定夺什么（修/建缺陷/回澄清）。

**纪律**：
- 五段齐全禁追问——呈报完对方无需再来回问细节就能定夺；
- 两可时不擅自分流，呈报让对方定；
- 定夺后按"四源回写"落册（SYS 修正/DEF 新增/IMP 行为固化/CHG 需求变更），原正文不动、增量承载、失效条打标。
