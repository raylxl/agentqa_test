## 18. 交付物命名规范（v2.9 新增 · 2026-11-04 用户拍板固化；原标 §16 与 §16 通用计费答疑沉淀撞号，v2.12 编号修复改 18）

### 18.1 版本号形态（铁律）

1. **版本号只用整数递增**：`v1 / v2 / v3 …`（对齐上游《测试用例设计通用规范_v3》§5.3）。
2. **废止两类形态用于文件名**：小数（`v1.1`）与下划线混合（`v1_1`）。
3. **升号时机**：修订并重新交付（MD 或 XMind 任一）即升整数号、以新文件名存档，旧版文件原位保留。
4. **细粒度修订轨迹**：留在文内"修改记录/版本表"，不进文件名（例：正本 v2 文内可载 v1.1→v1.3 的历史轨迹描述，但文件名只出现 v2）。

### 18.2 同文件类型名称一致性（铁律）

同族同类交付物统一命名模板，**禁止单册自创短名**（2026-11-04 配送价格证书 `配送价格_用例v1_完成证书.md` 短名即本条来源）：

| 文件类型 | 命名模板 | 位置 |
| --- | --- | --- |
| 用例正本 / XMind / Excel | `财务需求{YYYY}_{模块}_{菜单}_{批次}_测试用例_v{N}.md / .xmind / .xlsx` | 用例文件目录 |
| 完成证书 | `财务需求{YYYY}_{模块}_{菜单}_{批次}_用例完成证书_v{N}.md`（单文件持续维护，版本轨迹在文内版本表；被取代旧档后缀 `_旧档v{N}`） | 用例文件目录 |

1. **文件更名 → XMind 必须重出**（上游 §5.4：XMind L1 以文件名为正源），三步全绿（生成→结构验证 0 错 0 警→数据终验差异=0）。
2. **文件更名 → 全库引用同步**（证书/报告/记忆中的旧文件名引用一并更新）。
3. **新增文件类型先定模板再用**：族内无先例的新类型文件，命名先入本表再落盘，不再出现孤儿短名。

1. **最高版本号文件 = 唯一现行版**，恒为最新、最全（含全部历史修订的累计内容）；执行人/复用方只认每册最高版本号文件。

## 19. Excel 表格用例交付（双格式之二·2026-11-05 立）

- **双格式并列**：用例正本（MD）确认后交付 **XMind 与 Excel** 两种成品——同源、同 stem、同版本号（`_v{N}.xlsx`）；Excel=外部消费兼容格式（平台导入/AI 执行池/人工执行清单），XMind=浏览评审格式；
- **生成链**：`MD转XMind生成工具集\07_新标准工具链\md2xlsx_v1.py`，三步内置（生成→结构校验→数据终验差异=0 才交付）；输入与 XMind 链同（五列竖排/横排 row5/七列 row7 自动识别）；
- **列集**：外部《测试用例生成提示词》14 列**超集=16 列**（+判断依据+测试方法）——判断依据为内部溯源正 Column，导出禁丢；
- **铁则**：①执行三列（实际结果/测试原因/验证截图）**留空**——设计/执行分离（00 索引外部对照裁定③），执行态记 UI 报告/证据链执行回填口径：**通过=断言结果摘要**（响应/行数/文案命中），**不通过=截图+预期 vs 实际 diff**——禁「通过」零证据（对齐执行反馈闭环 §九 5 分钟审计标准）；②PRE 独立 Sheet 非用例不计条、无 TC 附表不进（同 XMind 规则）；③场景类型由测试方法映射（原始方法保留在列）；④执行方式**三态**：TC-API 前缀→api；预期/判断依据含「转测校准」→**manual_only**（人工件，执行池自动分流）；其余→ui；
- **Sheet 结构（对齐参考《货量考核政策_标准测试用例.xlsx》/AI 测试规范 §2.1·§7.2）**：①需求映射表（banner+requirement_id=REQ-{节号}/需求名称/需求描述/关联用例/关联风险）②测试用例（R1 即表头；在外部 14 列超集+判断依据+测试方法基础上增加逐 TC「关联风险」「执行集」两列，均从治理 JSON 派生；新册缺逐 TC risk_id 或执行集映射时硬失败）③公共测试数据（banner，承载 PRE）④统计与说明（内部溯源用，消费方可忽略）；执行三列交付留空、由执行方回填（通过/不通过+原因+截图），内部执行记录仍以 UI 报告/证据链为正本；场景类型=功能/边界/异常三态（测试方法+负向关键词推断）。历史豁免册可沿用无治理 JSON 的历史导出兼容路径。

### 20.3 数据来源与一致性铁律

1. **数据来源**=执行账本 JSON（逐条状态明细），报告统计**必须从账本脚本汇总**，禁手算；
2. **数字一致性**：报告各处出现的同一个数字（如 PASS 393）必须与账本汇总一致，改账本后报告同步刷新；
3. **真发现五要素**缺一不出报告（操作/预期/实际/证据/建议）；
4. **跨菜单发现**须标注影响范围（如"报价框架层通用缺陷，配送/平台/仓内三菜单实证"）；
5. **缺陷锚点（2026-11-12 立）**：已建单的失败条目必须携带缺陷单号与状态——审计链"需求→TC→Execution ID→缺陷单"全链可跳，从报告到缺陷平台禁靠人肉搜。

### 20.4 禁忌

- 禁"抽测"字样出现在报告正文——要么全量执行，要么明确列出未执行范围及原因；
- 禁零证据 PASS——每条 PASS 在账本有断言明细，报告抽样引用；
- 禁 BLOCKED 不说明原因——每条 BLOCKED 须归因（通道受阻/数据不足/引用此前实证）+ 处置建议；
- 禁报告版本号独立递增——跟随用例版本号，不因报告自身修订而单独升号；
- **禁只开头清一次弹窗——每个操作步骤前都必须检测关闭（细则§十二.1），弹窗是系统行为不可控，执行引擎必须自适配；
- 禁不清理上轮数据就开跑**——每轮执行前必须清理上轮 TEST_* 数据或用全新日期域隔离（细则 §十二），否则判重撞库=正向用例白跑。

### 20.5 测试结果状态分类铁律（2026-11-08 立，用户纠偏"没执行到位就报问题"）

测试报告中**必须严格区分**以下四种状态，禁止混用：

| 状态 | 含义 | 使用条件 |
| --- | --- | --- |
| **PASS** | 测试执行完成，系统行为=用例预期 | 断言全部通过 |
| **FAIL** | 测试执行完成，系统行为≠用例预期 | 断言失败且**已观察到系统实际返回** |
| **NOT_EXECUTED** | 自动化未执行到位，无测试结论 | 脚本超时/页面未加载/操作未完成——**系统行为未知，禁标FAIL** |
| **BLOCKED** | 测试通道受阻（环境/工具/数据不足） | 导出下载/复杂构造等 |

**核心规则**：
1. **FAIL 只用于"跑到了断言且断言失败"**——如果连保存都没点到，系统没返回任何结果，标 NOT_EXECUTED
2. **NOT_EXECUTED 禁止附带风险描述**——不能写"影响计费准确性"等暗示系统有问题的表述，因为**没有证据**
3. **NOT_EXECUTED 的处置=列人工补测清单**——写清楚"要验证什么+怎么操作"，不写"可能有什么风险"

### 20.4A 每轮报告同步与五要素（2026-11-13 立，用户拍板"有规范必须执行"+"每轮都要知道做了什么"）

**每轮块五要素**（缺一即不合格；已并入 §20.2 冻结模板轮次块 12 字段，本节为字段定义出处）：
1. **做了什么**——本轮执行范围（条数/章节）+结果分布
2. **做了多久**——起止时间+耗时（来自 run_start/run_end，§6.6）

4. **为什么这个轮次只执行这些**——范围边界原因（拍板挂起/依赖环境/攻坚优先级）
5. **剩下的为什么执行不了**——逐条阻塞原因（等 Mock/等修复/数据依赖/通道限制）

### 20.6 PASS 判定标准（2026-11-08 立，用户质疑"PASS 到底验证了什么"）

**PASS 的最低门槛**：至少一个**实质断言**验证了系统可观测状态与用例预期一致。

| 等级 | 断言类型 | 可否标 PASS |
| --- | --- | --- |
| **强** | colAllMatch/impOk/rowColVal/msEcho/echo/formDefault/headCols | ✅ PASS |
| **中** | dlgGone/blocked/rowHas/total/impBlocked/empty/snapHas | ✅ PASS（但报告须注明断言强度） |
| **弱** | dlgStay/dlgTitle/badgeState/effTabFilter | ⚠️ 临时弱断言标签；不得直接形成最终 PASS |
| **无** | any/totalAny/无断言 | ❌ **最终结果=NOT_EXECUTED**（无实质验证） |

**四条铁律**：
1. **any 断言禁标 PASS**——操作没报错≠系统行为正确，最终结果落 NOT_EXECUTED，原因标“无实质断言”
2. **PASS 必须有证据**——至少一条断言检查了系统的可观测状态（弹窗状态/列表数据/提示文本/输入框回显）
3. **dlgGone 单独不够**——弹窗关闭可能是保存成功，也可能是被 clearPopups 误关，需配合列表查询/详情比对
4. **报告须披露断言强度分布**——强/中/弱/无 各多少条，让读者知道 PASS 的可信度
### 20.7 失败条目自包含标准（2026-11-09 立，用户指出"还得追着问填的是哪个控件"）

报告中每条有问题的数据（FAIL/待拍板/缺陷证据），归类统计之外**必须逐条展示操作详情四要素**，不许让读者反问：

1. **控件全名+位置**（如"新增弹窗·重量明细一段·首价（元）输入框"，禁写"明细值"这类模糊指代）
2. **实际输入值**（自动化填了什么/人工输了什么）
3. **系统实际读回/响应**（输入框回显、接口返回、页面提示——原文照录）
4. **用例预期值 + 需求原文依据**（字段定义的精度/范围原文）

涉及可复现问题的，附**复现路径**（菜单→控件→输入→观察点，人工 30 秒可复）。已有五要素详述（操作/预期/实际/证据/建议）的条目视为满足；表格类清单若只给结论不给四要素=不合格，须展开。

> 来源教训：配送价格报告 v2 §4.2B 精度截断三条只写"明细首价超精度（如 2.5x）"，用户追问"TC-ADD-153 是哪个控件填 2.51"——报告不自包含，读的人要来问，耽误双方时间。此为"报告自包含"教训（2026-11-08 §四.2 逐条展开）在数据明细维度的延伸。

**四要素之上的第零要素（2026-11-09 补，用户"你再骗我"教训）：结论必须有实存证据。**"保存成功"必须以列表实查到该数据或成功 toast 为证，禁以未刷新 DOM 行/断言巧合推断；"系统展示了 X"必须以截图或 DOM 快照为证。报告里每一条缺陷候选/行为断言，先自问"这条结论推翻的证据链在哪"，没有实存证据的观察一律写"待实证"而非结论。
