# 鲸天系统 AI 自动化测试 · 用例编写标准 v1.0

> 目的：让项目管理中心用例库中的功能用例，能被 AI 编译器**确定性**转换为"可执行动作序列 + 可判定断言"，在鲸天系统（jt-ll.test.ztoeco.com）上自动执行、自动比对预期、不一致自动建缺陷。
> 适用范围：纳入 AI 自动化执行池的所有 UI 功能用例，包括人工编写的存量用例和 AI 生成的用例草稿。

---

## 0. 三条总原则

1. **一步 = 一个操作 + 一条可判定预期**。AI 按步骤编译动作、按预期生成断言，缺任何一半该步骤就无法执行或无法判定。
2. **元素指代必须用页面可见文案**。AI 靠页面文字定位元素，用例里必须出现按钮文字、字段标签、列名、菜单名。
3. **预期必须可判定**。"页面正常/显示正确/功能正常"属于不可判定写法，一律退回重写。

---

## 1. 用例整体结构（字段标准）

| 字段 | 必填 | 要求 |
|---|---|---|
| 用例标题 | 是 | 格式：`【模块-子功能】验证点描述`，一句话说清验证什么 |
| 模块/需求/迭代关联 | 是 | 在 PM 用例库中关联，缺陷建单时自动带上 |
| 优先级 | P0/P1/P2/P3 按 L1《通用用例设计标准》§1.1 与 L5 风险策略判定；此处不另行定义级别 |
| 前置条件 | 是 | 编号列表，必须可准备、可检查（见第 4 节） |
| 测试数据 | 是 | 变量表（见第 5 节）；无特殊数据可写"无" |
| 步骤 | 是 | 有序步骤列表，每步含操作+预期（见第 2 节） |
| 后置清理 | 否 | 需要回收数据时写明清理动作 |
| 自动化标记 | 是 | `可自动化` / `部分自动化(注明人工步骤)` / `暂不自动化(注明原因)` |

## 2. 步骤编写标准（核心）

每一步骤由两部分组成，在 PM 用例库中分别填入"步骤描述"和"预期结果"：

- **操作（Action）**：一个原子动作，动词开头，只做一件事。
- **预期（Expected）**：本步操作完成后可观察、可判定的结果。

### 2.1 操作动词表（封闭集合）

AI 编译器只认以下动词类别，写操作时必须从表中选用：

| 类别 | 允许的写法示例 |
|---|---|
| 导航 | 打开菜单「运单管理-创建运单」；访问页面「/waybill/create」 |
| 输入 | 在「运单号」输入 `${运单号}`；清空「备注」；在「附件」上传文件 `${附件路径}` |
| 点击 | 点击「保存」；双击表格行；右键「列头」；悬停「更多」 |
| 选择 | 在「客户」下拉选择 `${客户名称}`；勾选「第一条记录」；切换到页签「明细」；单选「加急」 |
| 表格 | 在表格第 `${N}` 行点击「操作-编辑」；在「状态」列筛选「待揽收」 |
| 弹窗 | 点击「确认」接受弹窗；关闭提示「操作成功」 |
| 等待 | 等待「保存成功」提示出现（**只允许等元素/提示，禁止写"等待 3 秒"这类时间等待**） |
| 校验 | "查看"/"验证"开头的纯断言步骤（无页面操作） |

**写法规则：**
- 复合动作必须拆开：「填写所有信息并点击保存」→ 拆为输入步骤 + 点击步骤。
- 元素指代禁止"那个按钮/上面的框/左边的输入框"，必须写页面可见文案。
- 数据一律用变量 `${变量名}` 占位，禁止在步骤里写死具体值。

### 2.2 预期断言表（封闭集合）

预期必须能映射到以下断言类型之一：

| 断言类型 | 允许的写法示例 |
|---|---|
| 元素断言 | 页面出现「创建运单」表单；「删除」按钮消失 |
| 文本断言 | 「客户」字段显示 `${客户名称}`；提示文案显示「保存成功」 |
| 列表断言 | 列表共 `1` 条；第一行「状态」列显示「待揽收」 |
| 状态断言 | 「保存」按钮置灰不可点击；单据状态变为「已创建」 |
| 弹窗断言 | 出现确认弹窗，内容包含「确认提交」 |
| 接口断言（进阶） | 「创建运单」请求返回成功，且返回的 `status` 字段为 `CREATED` |

**禁止的预期写法**（一律判定为不可自动化，退回）：
- ❌ 页面正常 / 显示正确 / 功能正常 / 数据正确
- ❌ 模糊量词：「显示了很多记录」「速度很快」
- ❌ 不可观察的内部行为：「数据库写入成功」（除非改写为接口断言）

## 3. 用例粒度标准

1. 一条用例只验证**一个场景一个验证点**（一条正向路径 或 一条反向路径），不混用。
2. 步骤数建议 3~10 步；超过 10 步考虑拆分为多条用例。
3. 一条用例必须是一个**可独立建缺陷的单元**：任意步骤失败都能对应到一个明确的缺陷描述。
4. 反向用例单独成条，标题注明预期失败：`【运单管理-创建】验证必填缺失时保存被拦截`。

---

## 4. 前置条件标准

- 只写**可由系统准备或可自动检查**的条件，每条可执行：
  - ✅ 已登录鲸天测试环境，当前租户为「测试租户A」
  - ✅ 存在状态为「待揽收」的运单 `${运单号}`（由前置用例创建或平台造数）
- ❌ 不允许："联系开发准备数据""手动造一批单据"——若确实需要，标记该用例 `部分自动化` 并注明人工步骤。
- 前置数据建议链式复用：上游用例的产出变量作为下游用例的前置（平台按执行顺序传递）。

---

## 5. 测试数据标准

变量表字段：`变量名 | 取值方式 | 示例/规则`。

取值方式只有四种：
| 取值方式 | 含义 | 示例 |
|---|---|---|
| 固定值 | 每次执行相同 | 客户名称 = 测试客户A |
| 唯一生成 | 执行时自动加时间戳后缀防冲突 | 运单号 = `YT${时间戳}` |
| 前置产出 | 由本用例前序步骤或上游用例返回 | 运单ID = 步骤2返回的单号 |
| 环境注入 | 登录账号、租户等由平台环境配置注入，不写在用例里 | 登录账号 = {env.test_user} |

要求：
- 涉及**写操作**的业务主键（单号、名称）必须用"唯一生成"，避免污染和并发冲突。
- 账号、密码、租户等环境信息一律环境注入，禁止明文写入用例。
- 有清理要求的写用例补充后置清理步骤（或标记由平台定期清理测试数据）。

## 6. AI 生成用例：设计方法与生成流程

AI 生成用例不采用”一个正向加几个反向”的固定套路，而是**先解析需求 → 按需求特征选用经典设计方法 → 按方法产出规则生成 → 覆盖自检**的四步流程，确保每个功能点用了什么方法、覆盖了什么，都有据可查。

### 6.1 生成流程（四步）

1. **需求解析**：AI 从 PRD/需求条目提取《需求要素清单》，固定结构输出：
   - 功能点列表
   - 输入字段及约束（类型 / 长度 / 必填 / 枚举取值 / 数值范围 / 默认值）
   - 业务规则（”条件 → 结果”的 if-then 形式）
   - 业务流程与状态流转（流程节点、分支、状态机）
   - 角色与权限
   解析结果随用例草稿一起输出，供审核人核对需求无遗漏、无理解偏差。
2. **方法匹配**：按 6.2 的矩阵为每个功能点选择设计方法，可多选叠加。
3. **用例生成**：按所选方法的产出规则（6.2 第三列）和本标准格式逐条生成。
4. **覆盖自检**：AI 随附《覆盖自检表》（6.4），列明每个功能点用了哪些方法、覆盖了哪些等价类 / 边界 / 规则列 / 迁移路径。

### 6.2 需求要素 → 设计方法选择矩阵

| 需求要素特征 | 选用方法 | 用例产出规则 |
|---|---|---|
| 有输入字段/表单（文本、数字、日期、文件） | 等价类划分 + 边界值分析 | 有效等价类尽量合并在正向用例中；**每个无效等价类单独一条**；数值型必测上/下边界及边界±1；长度型必测 0、最大、最大+1；枚举型每个取值至少出现一次 |
| 多条件组合决定结果的业务规则 | 判定表法（条件间有约束时先用因果图梳理） | 列全条件桩与动作桩生成判定表，**每条规则列至少 1 条用例**；组合数 >20 时先精简无关条件，仍过多转正交法 |
| 端到端业务流程（创建→审核→揽收→签收…） | 场景法 | 基本流 1 条；每个备选流（取消、驳回、超时、中断恢复）至少 1 条 |
| 单据/运单状态流转 | 状态迁移法 | 每个合法迁移 1 条；每个典型非法迁移（如已作废单据再编辑）1 条 |
| 多参数组合查询/筛选/配置项 | 正交实验法（成对组合 pairwise） | 全组合爆炸时按两两组合生成，并说明正交表选用依据 |
| 历史缺陷高发/易错点 | 错误推测法 | 平台将 PM 缺陷列表中该模块历史缺陷喂给 AI，针对性补强用例 |
| 多角色权限 | 角色-功能矩阵 | 每个角色”有权操作成功 / 无权被拦截”各 1 条 |
| 并发/时序类（库存扣减、重复提交、幂等） | 并发场景设计 | 标记”部分自动化”，或下沉到接口层执行 |

### 6.3 数量与优先级控制（防用例爆炸）

- 单个功能点 UI 用例常见区间 **5~15 条**；超出时 AI 必须说明原因，或建议将枚举穷举、罕见组合**下沉到接口层**（衔接”UI 执行沉淀接口用例”的分层策略）。
- 优先级映射：P0 = 场景法基本流 + 判定表主规则 + 主边界；P1 = 备选流 + 其余边界 + 权限；P2 = 罕见组合与错误推测补充。

### 6.4 覆盖自检表（AI 必须随用例草稿输出）

| 功能点 | 选用方法 | 覆盖项（等价类/边界值/规则列/迁移路径） | 用例编号 |
|---|---|---|---|

审核人按此表核对三件事：字段有没有漏做等价类、判定表规则列全不全、备选流和非法状态迁移有没有遗漏。

### 6.5 附加要求

1. **来源标记**：AI 从需求文档生成的用例标记 `AI生成-待审核`，人工审核通过后才进入执行池，审核动作记录留痕。
2. **同标合规**：AI 生成用例与人工用例执行同一套标准（动词表、断言表、变量规范），不符合即视为生成失败自动重生成，不带病入库。
3. **审核检查清单**（人工审核时逐项确认）：
   - [ ] 需求要素清单无遗漏、无理解偏差（功能点/字段/规则/流程/角色）
   - [ ] 方法选择合理，覆盖自检表与实际用例一致
   - [ ] 步骤在鲸天页面上真实可操作（菜单/按钮确实存在）
   - [ ] 预期与需求描述一致，且可判定
   - [ ] 测试数据可构造、可清理，粒度合规（一用例一验证点）

## 7. 可自动化性评级（存量用例摸底/验收用）

对存量用例按四个维度打分，用于摸底统计和整改排序：

| 维度 | 检查项 | 不满足时的整改 |
|---|---|---|
| A 结构完整 | 有前置条件、步骤、预期分层 | 补齐结构 |
| B 动词规范 | 每步操作可映射动词表 | 改写步骤描述 |
| C 预期可判定 | 每步预期可映射断言表 | 补/改预期描述 |
| D 数据可构造 | 变量四种取值方式之一，写操作有唯一性 | 补测试数据方案 |

评级结论：
- **A/B/C/D 全满足 → 可直接自动化**
- 缺 C → 补预期后可自动化（占比通常最高的整改类型）
- 缺 B → 需改写步骤（工作量中等）
- 缺 D → 需数据准备方案（部分转"部分自动化"）

验收目标：核心模块（P0/P1）存量用例可自动化率 ≥ 80%。

## 8. 合格示例（鲸天·创建运单）

> **用例标题**：【运单管理-创建】验证必填信息完整时创建运单成功
> **优先级**：P0　**自动化标记**：可自动化
> **前置条件**：
> 1. 已登录鲸天测试环境，当前租户为「测试租户A」
> 2. 存在可用客户档案 `${客户名称}`
> **测试数据**：
>
> | 变量名 | 取值方式 | 示例/规则 |
> |---|---|---|
> | 运单号 | 唯一生成 | `YT${yyyyMMddHHmmss}` |
> | 客户名称 | 固定值 | 冷链测试客户A |
> | 备注 | 固定值 | AI自动化回归 |
>
> **步骤**：
>
> | # | 操作 | 预期 |
> |---|---|---|
> | 1 | 打开菜单「运单管理-创建运单」 | 页面出现「创建运单」表单 |
> | 2 | 在「客户」下拉选择 `${客户名称}` | 「客户」字段显示 `${客户名称}` |
> | 3 | 在「运单号」输入 `${运单号}` | 输入框内容为 `${运单号}` |
> | 4 | 点击「保存」 | 出现提示「保存成功」 |
> | 5 | 切换到页签「运单列表」 | 列表第一行「运单号」列显示 `${运单号}`，「状态」列显示「待揽收」 |
>
> **后置清理**：作废运单 `${运单号}`

### 反例对照（同场景的不合格写法）

> ❌ 标题：测试创建运单
> ❌ 步骤：1. 输入所有必填信息，点击保存
> ❌ 预期：页面正常，保存成功
>
> 不合格原因：复合动作未拆分；"所有必填信息"无变量定义；"页面正常"不可判定；无元素文案无法定位。

## 9. 附：编译后的内部交换格式（平台内部使用）

人工/AI 用例按本标准编写，平台编译器将其转换为如下结构化格式缓存执行（用例版本变更时重编译）。此格式仅供平台内部与排查使用，**用例作者无需手写**：

```yaml
case_id: PM-2026-000123
case_version: 3
title: 【运单管理-创建】验证必填信息完整时创建运单成功
priority: P0
preconditions:
  - type: login_env
    tenant: 测试租户A
  - type: data_exists
    entity: 客户档案
    where: { name: "${客户名称}" }
variables:
  运单号: { gen: "YT${ts:yyyyMMddHHmmss}", unique: true }
  客户名称: { const: 冷链测试客户A }
steps:
  - action: navigate_menu
    target: { menu: [运单管理, 创建运单] }
    assert: { type: element_visible, target: 创建运单表单 }
  - action: select
    target: { label: 客户 }
    value: "${客户名称}"
    assert: { type: text_equal, target: 客户, value: "${客户名称}" }
  - action: click
    target: { button: 保存 }
    assert: { type: toast_contains, value: 保存成功 }
cleanup:
  - action: api_call
    desc: 作废运单 ${运单号}
```
