# 缺陷模板与提单接入规范 v1（L6 执行层·缺陷模板）

> 定位：**平台无关的缺陷单字段模板正本 + 提单接入（适配器）契约**。模板与落单工序一次定死，接哪个缺陷平台随时可换——换平台=换适配器，模板与历史呈报零变动。严重度四级/分类五型/修复后回归口径正本=《执行反馈闭环标准》§八（本文只引用不复制）；已建单条目必须携带单号回填报告锚点=《交付物规范》§20.3 第 5 条。
>
> 建立日期：2026-11-16｜触发：用户拍板"缺陷模板平台化+接入入口可插拔"，"修复回归要求"升必填字段。

---

## 一、缺陷单模板

### 1.1 标题句式（一行式，任何平台都能装）

```
[{需求标识}] {菜单/模块}-{现象一句话}-{严重度}
例：[需求A] 报价维护-无匹配报价时整单不生成账单-P0
```

### 1.2 字段定义（三组）

**核心必填**（缺一不算合格缺陷单）：

| 字段 | 类型 | 约定 |
| --- | --- | --- |
| title | text | 按 1.1 句式；现象一句话说清"什么操作→什么结果" |
| module | text | 所属菜单/模块（与标题句式中的菜单一致） |
| case_id | text | 关联 TC 编号（多个分号隔）——审计链锚点，禁空 |
| severity | enum | P0~P3 四级（口径=闭环§八；是 defect_severity，与 case_priority 隔离，禁因严重度直接改用例级别） |
| category | enum | 分类五型（闭环§八）；**仅"功能缺陷"建单**，其余四型走各自闭环不建单 |
| steps | text | 编号复现步骤，**含造数前置**（数据怎么来的写清楚，别人能照着复现） |
| expected | text | 预期=**引用口径出处**（理解说明编号/需求原文章节），不写自由发挥的话 |
| actual | text | 实际=系统返回**消息原文照抄**，禁转述禁概括 |
| evidence | 附件清单 | 证据三件套：UI 截图×2（操作前+报错时）+ 接口 json + 带注释入参；附执行号（Execution ID / AX-*） |
| environment | text | 环境+租户+操作账号+代码版本（可取则附） |
| **规则依据** | text | **必填**：R-xxx 规则编号 / 需求文档章节 / 理解说明拍板编号 / **开发知识库 RB·IF 卡编号**（如 RB-004、IF-waybill-send-bill，2026-11-17 v1.2 扩认——公司层 wk_kb 适配器接线；卡＝系统现状侧证据，与拍板编号并列可选其一）——无依据不许提 |
| **判定过程** | text | **必填·四闸门留痕**（见 1.5）：审计时能看清排除了什么 |
| 复现率 | enum+text | 必现 / 偶发（附大致概率，禁止只写"偶现"） |
| 修复回归要求 | text | **关联用例+影响面用例清单**——修复后回归环节直接照此执行（2026-11-16 用户拍板由可选升必填） |
| dedup_key | text | **查重键**=TC 编号+步骤号+差异类别；建单前必先查重，**命中同键只追加证据、不重复建单** |

**条件必填**：

| 字段 | 触发条件 | 约定 |
| --- | --- | --- |
| 影响面 | severity=P0/P1 必填 | 波及流程+关联用例数+影响机构+**是否可绕过（怎么绕）**；金额/额度类缺陷一律先按 P0 处理再降级，且必须做守恒校验（扣减方+返还方=初始值） |

**可选**：

| 字段 | 约定 |
| --- | --- |
| requirement_ids | 关联需求编号（多个分号隔） |
| source | 来源标记（如"AI自动化"），由适配器落单时填写，人工呈报不填 |

**平台侧生成**：

| 字段 | 约定 |
| --- | --- |
| defect_id | 平台生成后**必须回填**报告缺陷锚点（交付物§20.3 第 5 条：审计链"需求→TC→Execution ID→缺陷单"全链可跳）+ 附B 呈报-拍板台账行 |

### 1.5 判定四闸门（提缺陷前置排除，2026-11-17 吸收自《生成缺陷的标准与模板_鲸天TMS_v1.0》）

**一个异常在排除四件事之前，不是缺陷**——判定过程按四闸门依次过并留痕进单内"判定过程"节：

```
异常 → ①用例闸门 → ②环境闸门 → ③数据闸门 → ④规则闸门 → 才是缺陷
```

| 闸门 | 排查什么 | 典型误报形态（来源件实战教训） |
| --- | --- | --- |
| ①用例本身对吗 | 预期是否来自规则原文（不是历史现象/静态快照）；数据前置是否写进用例；断言方式是否适配系统特性 | 预期写"页签全集"而实际是数据驱动懒渲染——用例错不是页面错；静默拦截类只看 UI 无反应漏断网络层 |
| ②环境正常吗 | 子应用真加载了；token/会话有效；重试 1 次是否消失 | 重试后消失=环境/超时定性+复现概率，不算缺陷 |
| ③数据前置满足吗 | 单据状态前置齐；状态残留/脏数据（先清后验）；环境数据边界 | 前一单未清理导致列表脏数据 |
| ④规则怎么说（定性） | 与规则原文明确冲突=实现缺陷；规则未覆盖且违反直觉=**需求歧义走回答疑不当缺陷提**；仅测试环境=环境问题；残留导致=数据问题；文案类=文案缺陷 P2 批量提 | 与五型分类（闭环§八）同源，此处为判定流程形态 |

AI 场景追加红线：禁止把 AI 推断当规则（expected 只能来自规则库/需求原文）；禁止无证据断言；禁止跳闸门；误报教训回写知识库（同一个坑只踩一次）；判不了升级人工不硬定性。

### 1.3 生命周期

```
新建 → 待确认（人工确认后进入流转） → 修复中 → 待回归 → 关闭
                                              └→ 重开（附失败证据）
```

- 创建后初始状态=**待确认**：建单只是"指控待核"，人工确认后才算正式缺陷；
- 修复后回归按单内"修复回归要求"字段执行：关联用例+影响面用例全过 → 关单附执行证据；不过 → 重开附失败证据。

## 二、适配器契约（接入入口可插拔的关键）

缺陷平台接入一律写成**适配器（adapter）**，模板正本永不感知平台差异。每个适配器必须提供四项能力：

| 能力 | 签名 | 作用 |
| --- | --- | --- |
| 提单 | `create(defect) → defect_id` | 按模板字段建单，返回平台单号 |
| 更新 | `update(defect_id, patch)` | 补证据 / 改状态（含追加证据式查重命中） |
| 查询 | `query(filter)` | 按条件查单（状态跟进、锚点回填、四源盘点拉单） |
| **字段映射表** | 内置声明 | 模板字段 ↔ 平台字段逐一对应；**平台装不下的字段按固定格式拼进描述区**（`【字段名】内容` 逐段），禁丢弃——保证换平台信息零丢失 |

规则：

1. 换平台=换 adapter 文件，模板、落单工序、历史呈报格式零变动；
2. 适配器不含业务判断——severity 映射（如本模板 P0~P3 ↔ 平台高/中/低）、必填校验全部在适配器映射层完成，映射关系写进该适配器的字段映射表；
3. 当前接入哪个平台由公司配置 `integrations.defect_platform` 声明（enabled=false 即未接入）；未接入时落单走降级路径=呈报附完整模板内容、人工落单后回填单号（见 §四第 5 步）；
4. 适配器属公司层资产（家底），通用方法与字段契约在本规范，具体适配器实现不放通用层。

## 三、与既有体系关系（指针，不复制）

| 口径 | 正本 | 本文角色 |
| --- | --- | --- |
| 严重度四级 P0~P3 / 分类五型 / 修复后回归 | 执行反馈闭环标准 §八 | 引用；本文 1.2 的 severity/category 只放一句口径摘要 |
| 仅"功能缺陷"建单的分流判定 | 执行反馈闭环标准 §二 | 引用 |
| 已建单条目携带单号回填锚点 | 交付物规范 §20.3 第 5 条 | 引用并在 1.2 平台侧字段重申 |
| 五段式呈报（场景/操作/预期/实际/消息原文） | 执行反馈闭环标准 §三 + 手艺包五段式模板 | 落单工序第 1 步的前置输入 |
| 报告轮次块"缺陷单变化"字段 | 交付物规范 §20.2 | 单号来源=本规范落单回填的 defect_id |

## 四、落单工序（发现→拍板→落单→回归→关单）

1. **呈报**：执行发现按五段式呈报（闭环§三），一次一事，对话内文字拍板；
2. **拍板**：用户拍板"建缺陷"（分流①用例对、实现错）；两可时呈报不擅自分流（闭环§二铁则）；
2.5 **判定留痕**：按 §1.5 四闸门依次过并在单内"判定过程"节留痕（AI 误报第一防线——上游鲸天 TMS 实战：闸门①拦下的"用例错误"占误报大头）；
3. **查重**：按 dedup_key（TC 编号+步骤号+差异类别）查当前平台未关闭单——命中同键→只追加证据（update），不重复建单；
4. **填单落单**：按 §一 模板逐字段填齐（核心必填缺一不提）→ 经当前 adapter create 落单 → 拿到 defect_id；
5. **回填**：defect_id 回填报告该失败条目缺陷锚点 + 附B 呈报-拍板台账行 + 轮次块"缺陷单变化"字段；**adapter 未接入时**=呈报附完整模板内容（全部字段照 §一 填好），人工落单后把单号回填同样三处；
6. **状态跟进**：按 adapter query 跟进（待确认→修复中→待回归）；
7. **修复回归**：研发标记修复 → 按单内"修复回归要求"执行关联用例+影响面用例回归 → 通过=关单附执行证据；不通过=重开附失败证据；
8. **闭环销账**：关单后报告附A 余项清单销账，用例预期不变（缺陷修复不回头改用例，除非走 SYS 源拍板修码）。
