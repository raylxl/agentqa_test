# 执行反馈闭环标准 v1（L6 执行层）

> **定位**：用例**执行后**的反馈闭环正本——"实现与预期不一致/观察项/挂账项"的**呈报 → 拍板 → 修码 → 销账**全流程。设计期方法论在 L1~L4 各层；"用例怎么写才能被 AI 执行"在《执行期参考》（同层并列）。
> **来源**：2026-11-04 用户拍板起草（起因=用户问"执行后发现用例与系统实现不一致、等我确认后修改/补全用例，有这种机制吗"——零件散落未成文，立项补齐）。沉淀自 4 次真实闭环（配送自提翻转 Q38、通用计费 C3 流量费翻转、E1 计费舍入修订、平台节头清理）+ G16 分流原则升格。
> **治理**：只增不覆盖，文内修订记录递增并注明来源；**所有用例修改必须经用户拍板，禁自行按实现改预期**（"系统就这样"不构成修改依据）。

---

## 一、适用与触发源

适用于一切用例执行活动（UI 手工/AI 自动化/接口/抽测/回归）及其后续处理；非执行类发现渠道（代码走查/端到端审查/外部用例对比）复用同一闭环。触发源六类：

1. 执行观察（形态未定项，只记录不断言）
2. 执行失败（预期 ≠ 实际）
3. 待复验项复验
4. 转测校准挂账回填
5. 代码走查/审查发现
6. 外部用例对比发现

## 二、分流判定（核心·三选一）

实现 ≠ 预期时，**先查该条判断依据格出处，再分流**：

| 分流 | 判定 | 动作 | 用例 |
| --- | --- | --- | --- |
| ① **用例对、实现错** | 断言依据=拍板口径/需求原文/标准条款 | 建**缺陷单**（描述须引用 TC 编号+判断依据出处） | **不动** |
| ② **实现为准、用例口径旧/需求未定** | 开发确认实现口径/代码实证/用户说明 | 走第三节呈报 → **用户拍板后修码**（第四节动作链） | 修/补/删 |
| ③ **需求本身变** | 口径变化超出原拍板范围 | 回答疑闭环（五段式）重新拍板，评估影响面后批量修 | 批量修 |

两可时**呈报不擅自分流**（承通用 G12 呈报义务）。G16"门禁后置·按口径偏差/缺陷反馈"条款自本节升格承接（《报价政策族标准》§17 原文保留+指针指此）。

## 三、呈报格式（五段式·一次一事）

1. **现象**：环境 + TC 编号 + 步骤号 + 预期 vs 实际（截图/接口报文佐证）；
2. **用例原文与出处**：该条判断依据格内容 + 拍板/标准出处；
3. **系统实际表现**：可观测事实，不掺推断；
4. **分流初判**：三选一 + 理由；
5. **拍板请求**：修用例（附建议改法）/ 建缺陷 / 回答疑——用户文字回复即拍板。

## 四、拍板后动作链（当轮全量根治）

修码 → **登记回写台账（§十五四步铁律①）** → 结构门禁复跑（assemble 全绿）→ 受影响时 XMind 三步重出 → 文内修改记录加拍板行 → 证书版本行/台账同步 → **同口径全册扫描**（同模式当轮根治，禁只修单点）→ 缺陷线另跟进缺陷单状态（用例预期不变）。

多发现批量形态 = 台账化：逐项编号呈报/拍板/落码/销账。

## 五、转测校准挂账与销账

- **挂账**（G9 固定化）：理解说明/证书登记清单，用例内以"转测校准"句式标注（执行时记录实际形态、不作失败判定）。现行挂账：配送 2 项（单箱重量/箱数取值字段、子单数量口径）、通用计费 3 项（报缺失 list 细粒度、云仓业务域枚举、特殊标识枚举）；
- **回填闭环**：执行记录实际形态 → 呈报拍板定形态 → 用例改定形态断言 → **证书+理解说明台账双向划销**。

## 六、执行记录归档

- 执行工件（结果 json/截图/报文）归执行目录（jt_chrome\ 等）；
- **UI 测试报告 = 执行记录正本**（含系统观察/待复验清单，复验后更新状态）；
- 分章目录内执行记录勿动（组装源）。

## 七、与其他标准的衔接

- 通用 G12（呈报义务）→ 本册第三节为执行期形态；
- 门禁验收 §10 → 修码后复跑依据；
- 交付物 §18 → 版本/XMind 联动；
- AiCoding 平台"执行断言"类规范 → 本册为内部正本，分发版另出脱敏。

## 八、缺陷单与严重度（吸收外部《AI 测试规范》§5）

- **缺陷报告五要素**：TC 编号+判断依据出处（§二既有）＋复现步骤＋预期 vs 实际＋证据（截图/接口报文/断言 diff）；平台化后按结构化字段自动建档（defect_id/case_id/severity/category/steps/expected/actual/evidence/environment/code_version）；
- **严重度四级**：P0=核心流程不可用/资损/数据丢失；P1=主要功能不可用但有替代、或次要功能不可用；P2=不影响主流程/体验；P3=提示与样式；
- **与用例优先级隔离**：本处 P0~P3 是 `defect_severity`（实际缺陷影响），不是 `case_priority`（测试资源优先级）；不能因缺陷严重度改变就直接改用例级别，需按《通用用例设计标准》§1.1与《测试策略与风险治理标准》重新评估风险、影响面和回归集。
- **分类五型**对齐 §二分流：功能缺陷（→缺陷单）/环境问题/数据问题（执行侧自修）/用例错误（→拍板修码）/需求歧义（→回答疑）；
- **修复后回归**：研发标记修复 → 关联用例+影响面用例回归 → 通过关单附执行证据；不通过重开附失败证据。
- **字段级缺陷单模板与提单接入**（2026-11-16 立）：建单字段/标题句式/查重键 dedup_key/生命周期/提单适配器契约/落单工序八步见《缺陷模板与提单接入规范_v1》（L6 执行·缺陷模板）；本节仍为严重度四级与分类五型的口径正本。

## 九、证据链与可审计（吸收 §7）

- 每次执行生成唯一 **Execution ID**，绑定五要素：代码版本（commit SHA）/用例版本（文件名+内部版本）/环境快照/执行日志（只追加不可覆盖）/失败截图（E2E 建议录像）；
- 追溯链：**需求 → 风险 → 用例 → 执行记录 → 缺陷/变更 → 发布标准 → 上线观察**，正反双向可查（当前载体=理解说明/策略卡/风险矩阵/用例册/UI 报告/jt_chrome 工件；平台化后入结构化库）；
- 报告生成后不可修改，修订出新版本并记变更原因；**审计标准：随机抽任意用例，5 分钟内找齐完整证据链**。

## 十、执行引擎行为边界（吸收 §8，裁剪）

- 禁改被测系统代码、禁提交研发分支；测试环境可操作，**预发/生产绝对禁止**；
- 危险命令黑名单：无条件 rm -rf / DROP TABLE / 无条件 DELETE / 格式化 / 改系统配置；
- 敏感信息：日志与报告中手机号/证件/卡号脱敏，密码/Token/Key 不落日志；测试用合成数据，原则上不用生产数据（必须用时先脱敏）；
- 破坏性操作防护：删数据用例先备份；重启类用例确认可自动恢复；写操作前确认目标为测试环境。

## 十一、升级兜底（吸收 §9，对话形态）

| 触发 | 路由 |
| --- | --- |
| 需求歧义无法唯一推断 | 产品/业务（回答疑闭环） |
| 环境 3 连败（非代码原因） | 运维/测试 |
| 疑似数据安全风险 | 立即停止＋负责人 |
| 缺陷 vs 需求歧义两可 | **呈报不擅自分流**（§二铁则） |
| 涉合规/法律/资损判定 | 负责人人工决策 |

升级信息并入 §三呈报五段式，追加两项：**紧急度（高/中/低）＋建议路由对象**；人工决策结果记录并用于修正用例（回 §四动作链）。

## 十二、变更影响面与回归集（2026-11-05 立）

- **拍板/需求变更触发**（§三呈报拍板通过后自动进入）：
  1. **反查引用面**：按变更口径关键词/拍板编号 grep 全册，判断依据格引用同源处全部命中；
  2. **受影响集**＝预期或判断依据引用该口径的全部用例＋同机制兄弟场景（§四"同口径全册扫描"的具体化）；
  3. **回归集**＝受影响条目＋其正向对照条；修码后随结构门禁复跑，回归结果记入修改记录行；
- **缺陷修复回归**（§八既有）：关联用例＋影响面用例；
- 代码 diff→回归范围：平台化后按外部《AI 测试规范》§2.4 启用（挂账，见 00 索引台账）。

## 十三、执行完成后回写提案（四源主动盘点·2026-11-06 立）

**触发义务（本条核心）**：每轮用例执行（UI/接口/回归）**收尾时**，执行方必须**主动**完成四源盘点并向用户呈报"需不需要改"——**不等用户发现、不等用户指令**；用户只做拍板（逐条/整批/驳回），不做发起。回写一律在用户拍板后执行（冻结纪律不变）。

### 13.1 四源定义与载体

| 源 | 定义 | 载体模块 | 关键要求 |
| --- | --- | --- | --- |
| 源一·系统与用例不符 | 执行不一致项+缺陷单定案的行为与原用例预期冲突 | **SYS 章**（修正用例，**必须挂老用例编号**） | 断言按系统定案行为写 |
| 源二·缺陷数据新增 | 缺陷平台本菜单全量单（**已关闭=定案**）引入的原册没有的场景 | **DEF 章** | 拉单比对来源=ISS 单号 |
| 源三·实现行为固化 | 已落定的转测校准观察+实测合理行为+**需求未定义** | **IMP 章**（实现行为契约） | 判断依据统一标"**需求未定义·实现行为固化**"以区别需求用例；**同构场景须逐控件实测、禁推定**（先例：开关循环下订单类型多选=清空不回填、计费维度单选=数据同样清空但 UI 显示残留旧值——仅凭显示层会误判）；**断言终判以提交/落库结果为准，控件显示不作唯一判据**（先例：单选框显示残留旧值而直接保存被必填拦截，2026-11-06 决定性实验纠正） |

### 13.2 呈报格式（硬性）
| 源四·需求变更（2026-11-07 立，源=用户拍板"需求变更引起的用例设计需独立载体标识"） | 需求中途变更/补充：①全新需求点（原用例无对应）②变更推翻原预期需重造 | **CHG 章**（TC-CHG 前缀） | 判断依据标〔来源：需求变更 …（编号/日期/通知）〕；B 类重造条必须挂老用例编号，被推翻原条打失效标识、替代指针写 TC-CHG-xx；新开模块独立成节（或附录"需求变更记录"章），与本轮 SYS/DEF/IMP 不混编 |

- 候选必须按**完整五列表用例格式**逐条展示供确认——**一句话清单视为无效呈报**（用户无法确认，2026-11-06 反馈）；
- 每条标注来源（实测出处/ISS 单号/已落定观察）；IMP 类附"需求未定义"标注；
- 用户确认方式=整批"入"/单条调整（改预期、删条、调级）。

### 13.3 入册方式（增量式）

1. **原用例正文不动**；仅删除已证伪的拍板引用标记（断言正文保留，由 SYS 承接修正）；
2. 新模块承载全部变化（SYS/DEF/IMP/CHG 章，TC-SYS/TC-DEF/TC-IMP/TC-CHG 前缀），每条判断依据含**老用例编号（SYS）/"原用例无对应"（DEF/IMP）+〔来源〕**；
3. 入册后重组装过结构门禁。
5. **用例册统计摘要（文件头部必含·2026-11-09 立）**：每次组装/重出用例册时，文件头部统计表之前**必须自动生成"用例册统计摘要"块**——含：用例总数+P0/P1/P2、原始设计用例数（一~十六章）、其中已失效数（〔已失效〕标题计数）、其中有效可执行数、三个增量模块各自条数（SYS 系统与用例不符/DEF 缺陷数据场景/IMP 实现行为固化，各附一行说明）、有效可执行合计（=总数−已失效）。数据从分章源文件**程序化统计**（非手写），随每次重组装自动更新。执行者/管理者打开用例册第一眼即看到全貌（原始→变化→现状），无需翻查修改记录或执行记录。
4. **失效标识（全量执行安全·2026-11-06 立）**：被新模块替代且原预期已被推翻的原用例，**必须打失效标识**——标题文本划删除线＋尾标〔已失效〕（TC 编号前缀不划线，保持组装器可识别）；替代指针与原因落判断依据格（"〔已失效·执行跳过·替代：TC-SYS-xx｜源：…〕"）；**增强型/两可兼容型不标失效**，仅判断依据挂关联注记。全量执行遇〔已失效〕一律跳过、以 SYS/DEF/IMP/CHG 章对应条执行。替代指针按推翻来源分型标注：实现差异→TC-SYS/TC-IMP、缺陷定案→TC-DEF、需求变更→TC-CHG（源写"需求变更 …"）。

### 13.4 盘点来源与补测

- 执行记录（FAIL/校准/F 系发现/已落定观察）＋ 缺陷平台拉单（按菜单过滤，含状态流转）＋ 现场补测（盘点发现盲点时上环境实测拿实据，如同构控件行为）；
- 与 §十二联动：缺陷修复关闭→回归轮→回归收尾再触发一轮四源盘点（提案-拍板-入册循环）。

## 十四、呈报-拍板台账（问答在册，2026-11-10 立）

- 本册 §三呈报与用户拍板、§十三三源盘点及其拍板，**一律登记入该需求《测试报告》的「呈报-拍板台账」节**（交付物§20.8）：五列流水＝我提出的问题｜用户答复｜处置结果｜闭环日期｜Execution ID；只增不覆盖；
- §四动作链追加收尾步骤：**修码/销账完成后同步测试报告「当前余项清单」+登记台账行**——未同步即该轮未收尾；
- 台账=跨会话唯一事实源：会话记忆会过时，台账不会；任何会话报待办前先查台账（同§20.8）。

## 十五、拍板回写四步铁律与机检门禁（2026-11-13 立）

> 源=跨需求回写质检 17 红事故（总报告=用例文件\跨需求拍板回写质检总报告_20261113_v1.md）：附B 处置列写"已修订"但四载体零落地、正本改了分章没改、跨册拍板单册漏改——"报告自述=完成证据"模式全面失效。用户拍板"先落"本节根治。

**四步铁律（每条拍板产生回写义务时，按序执行，缺一即红）：**
1. **登记**：当场在 `{需求}分章\writeback_pending.jsonl` 追加一行（tc/field/new=可 grep 的锚点短语/status=pending/source=拍板出处）。形态类回写也必须给锚点短语（如"点击即拦/不标红"），禁空值逃逸；
2. **改分章**：用例修改一律先改分章（`*分章\*.md`），**禁直接改正本**——正本=组装产物（PreToolUse hook 已拦 Edit/Write 直改正本；全流程场景册无分章白名单例外）；
3. **组装正本**：跑 `_assemble.py` 重出正本（分章→正本单向流动）；
4. **锚点验证置 done**：`python D:/ZCodetest\jt_chrome\writeback_check.py - <正本.md> <分章目录> <pending.jsonl> <测试报告.md> [--defer-artifacts]` 全绿后，台账 status 置 done（ts=完成日）。**附B 处置列禁止单独作为完成声明**——"已修订"必须对应 done+锚点。

**双登记（跨册拍板）**：附B 写"N 册统一/连带"类处置时，**必须同步登记《需求流水线台账》拍板队列**分发各册（单册台账不是跨册事项的唯一载体——本次平台/仓内 12 条漏改即此断裂）。

**收尾机检门（硬闸，红了禁收尾/禁开工）**：
- `report_sync.py` 硬校验④：writeback_pending 残留=pending = 有拍板未落地 = 禁收尾；
- `writeback_check.py` 六查：①done 锚点逐条正文 grep（声明≠事实直接红）②账本启发式兜底 ③统计块=实文 ④正本/分章失效标注一致 ⑤附载体（挂起重出期用 `--defer-artifacts` 豁免，重出完成后撤除恢复硬查）⑥附B 完成性声明可追溯台账；
- 两个 hook：PreToolUse 拦正本直改 + PostToolUse 写《测试报告》时注入拍板对账提醒（重开会话生效）。

**挂账边界（如实声明）**：多会话并行编辑用例文件的锁机制未建（挂账）；"拍板漏识别"（该登记没登记）无技术强制，靠 report_sync 对账+hook 提醒+usecase-qc Q1 证伪三层兜底。
