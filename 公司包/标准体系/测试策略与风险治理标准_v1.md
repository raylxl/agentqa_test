# 测试策略与风险治理标准 v1（跨需求治理层）

> **定位**：把“需求来了以后测什么、测多深、何时算够、谁承担剩余风险”收口为一张可执行的治理标准。它不替代 L1 用例设计标准、L5 门禁或 L6 执行标准，而是把风险、优先级、测试深度、执行集、发布放行和上线观察串成一条链。
> **适用范围**：所有新需求、需求变更、缺陷修复回归、跨菜单/跨租户专项；低风险小改动可按本标准的轻量档执行。
> **治理**：只增不覆盖；本文件是风险治理与测试策略的唯一正本，其他文件只引用本文件，不重复定义同一口径。
> **关联正本**：用例优先级见《通用用例设计标准_v1》§1.1；执行集见本文件与《测试用例执行集裁剪与优先级规范》；设计门禁见《门禁验收标准》；执行反馈见《执行反馈闭环标准》。

## 1. 需求接收卡（开工前必填）

| 字段 | 填写要求 |
| --- | --- |
| 需求标识 | 需求名称、版本、提出日期、产品线、租户、菜单 |
| 变更类型 | 新增 / 优化 / 缺陷修复 / 需求变更 / 历史需求重出 |
| 影响面 | 菜单、角色、机构/租户、接口、数据库、批处理、账单/结算下游 |
| 业务目标 | 本次变化要解决的用户问题或业务结果 |
| 明确不测 | 本轮不覆盖的维度和理由，禁止留空 |
| 责任人 | 需求负责人、开发负责人、测试负责人、发布决策人 |
| 关联资产 | 理解说明、域标准、历史用例、缺陷单、接口基线 |

### 1.1 入口分级

| 档位 | 适用条件 | 最低流程 |
| --- | --- | --- |
| 轻量 | 单菜单、无金额/权限/数据隔离变化、无跨系统链路、低风险 | 接收卡 → 标准初判 → 聚焦答疑 → 风险/策略卡 → 用例与一次独立复核 |
| 标准 | 有状态、权限、接口、数据联动或中等影响 | 接收卡 → 标准定位 → 答疑闭环 → BRIEF/矩阵 → 生成 → 两员门禁 → 执行 |
| 完整 | 资损/计费、跨租户、账单结算、核心流程、合规安全、跨菜单链路或高不确定性 | 标准流程 + 风险—深度矩阵 + NFR分流 + 发布放行 + 上线观察 |

入口档位由最高风险决定，不能因用例数量少而降档。

## 2. 风险分诊与 P0123 映射

### 2.1 风险字段

每个风险项至少记录：`risk_id`、风险描述、影响（I）、发生概率（L）、暴露/可探测性（E）、风险责任人、初始等级、对应 P 级、测试深度、NFR维度、执行集、残余风险、接受人。

风险等级可用三档：

- **高**：一旦发生会造成资损、核心流程不可用、数据丢失/泄露、租户隔离失效、合规风险或不可逆业务错误；
- **中**：主要功能受影响但有替代路径，或重要状态/展示/接口行为错误；
- **低**：低频长尾、纯展示、一般体验或历史兼容，不影响主流程与数据正确性。

### 2.2 风险到优先级、深度和执行集（判据正本=通用§1.1，本表为映射摘要）

| 风险判断 | 用例优先级 | 最低设计深度 | 最低执行集 |
| --- | --- | --- | --- |
| 高风险，或命中资损/权限/数据隔离/核心主链/安全 | P0 | 正向 + 负向 + 边界 + 状态/时序 + 结果出口；必要时API/DB/账单双证据 | 冒烟、回归、变更；发布前必须执行 |
| 中高风险，影响重要规则、状态、主要异常或高频路径 | P1 | 正向 + 主要异常 + 关键边界 + 权限/联动视影响面 | 回归、全量或变更集 |
| 一般风险，普通边界、一般异常、重要展示/兼容 | P2 | 代表性正向/反向/边界；记录抽样理由 | 全量、专项或按变更影响执行 |
| 低风险长尾、纯装饰、极端组合、历史兼容观察 | P3 | 代表性抽样或人工观察；不得承担关键风险覆盖 | 专项/人工/抽样；默认不进日常回归 |

**硬性升档**：任何用例只要涉及资损、计费金额、核心状态主干、数据权限/租户隔离、敏感信息、安全暴露或不可逆操作，最低为 P0；不得以“场景低频”“实现简单”“只在UI上”降为 P1/P2/P3。

**只升不降**：同一需求点同时命中多条规则时取最高级别。P3 不是“不重要的需求”，而是“当前风险低、可延后执行的测试资源级别”。

**与缺陷严重度隔离**：用例优先级回答“设计/执行资源先投哪里”；缺陷严重度回答“实际缺陷影响多大”。二者都可用 P0~P3，但必须使用不同字段（`case_priority` 与 `defect_severity`），不得互相推导或直接改写。

## 3. 测试策略卡

每个需求至少有一张策略卡，包含：

1. 目标、范围、排除项和本轮结束要回答的上线问题；
2. 入口档位（轻量/标准/完整）及理由；
3. 风险清单与风险—覆盖深度矩阵；
4. P0/P1/P2/P3 预估分布及关键风险对应的 TC/章节；
5. 全谱系选择：功能、UI、性能、兼容、安全、可靠性、可用性、可访问性，逐项写“测/不测/理由”；
6. 测试通道：UI、API、DB/账单、人工、观察；
7. 执行集：冒烟、回归、全量、变更、专项，以及裁剪理由；
8. 入口条件、出口条件、阻断条件、置信度输出方式；
9. 发布决策人、残余风险接受人和上线后观察计划。

## 4. 执行就绪卡（分阶段）

执行就绪卡在设计阶段先建计划并持续更新，不把尚未部署的环境误判成设计缺陷；进入批量执行前再逐项确认并通过执行门。

### 4.1 设计阶段（design/verification）

- 必须存在 readiness 状态和构建、环境、账号、数据、证据出口等字段；未知信息可显式写 `TBD`，状态使用 `awaiting_environment` 或 `blocked`。
- 设计证书可以在 `awaiting_environment` 状态下签发，但必须明确“仅设计完成，未获执行放行”。


- readiness.status 必须为 `ready`，且构建号/部署时间/前后端版本与需求版本一致；
- 环境地址、租户、机构、账号、角色和权限可用；
- Feature Flag、依赖服务、Mock、接口、数据库和异步任务可用；
- 测试数据量、隔离前缀、清场与回滚方案已准备；
- 证据出口可用：页面、接口报文、账单/交易明细、日志或任务结果；
- NFR 工具和采集方式按策略卡触发范围可用；
- 每个阻塞项有状态、责任人、预计解除日期；
- 未满足项只能标记 BLOCKED/NOT_EXECUTED，不得伪装为 PASS。

### 4.3 发布阶段（独立休眠门）

生产/灰度发布决策与执行就绪分离；没有生产/灰度权限和真实证据时，保持休眠，不生成 Go/No-Go 结论。

## 5. 非功能测试分流

| 维度 | 触发条件 | 最小输出 |
| --- | --- | --- |
| 性能/容量 | 大数据量、批量导入导出、核心查询、用户明确关注 | 样本量、并发/数据规模、P95或吞吐、瓶颈和结论 |
| 可靠性/恢复 | 异步任务、重试、失败恢复、批处理、外部依赖 | 故障注入或中断点、恢复条件、数据一致性证据 |
| 兼容性 | 浏览器/分辨率/设备差异影响操作或展示 | 兼容矩阵、覆盖设备、差异与处置 |
| 安全/权限 | 角色、租户、敏感数据、接口直调、导出或详情直链 | 鉴权/越权路径、数据暴露结论、证据 |
| 可访问性/可用性 | 关键操作依赖键盘、颜色、提示或复杂交互 | 键盘/焦点/对比度/提示可理解性观察与结论 |
| 可观测性 | 发布后需监控业务或技术异常 | 指标、日志、告警、阈值和责任人 |

未触发的维度也必须在策略卡写明“不测及理由”，不能默认为已覆盖。

## 6. 设计、执行、发布三道出口

### 6.1 设计完成

- 需求疑问已闭环或按规则登记为不阻塞项；
- 风险清单、P0123分级、策略卡和必要矩阵齐全；
- 用例通过 L5 九项尺子与执行就绪度检查；
- 风险项均有 TC 或明确的观察/转测校准落位。

### 6.2 执行完成

- 计划执行集已全部落账为 PASS/FAIL/NOT_EXECUTED/BLOCKED；PENDING/OBSERVE 等临时态必须在报告前收敛；
- P0 按门禁要求 100% 通过；P1 按现行出口要求达到阈值；
- P2/P3 未执行、失败或人工项均有裁剪/处置理由；
- 所有风险项有证据、缺陷/变更/残余风险归属；
- 结论明确实际覆盖率和置信度，不以部分覆盖推出全量结论。

### 6.3 发布放行（Go/No-Go）

**No-Go**：P0 未通过、核心风险无证据、数据/权限/安全隔离未验证、发布回滚不可用、关键NFR超阈值且无批准豁免。

**Go with accepted risk**：仅允许剩余 P1/P2/P3 或非关键NFR风险，必须写明风险、影响、临时措施、接受人、有效期和上线观察项。

发布记录至少包含：决策、决策人、证据索引、残余风险、回滚触发和观察窗口。

## 7. 上线后观察

上线或灰度后按策略卡执行：

- 观察窗口：开始/结束时间、灰度范围、责任人；
- 技术指标：错误率、P95、超时、任务失败、告警；
- 业务指标：订单/账单/金额/结算异常、空结果或重复计费；
- 触发阈值：达到阈值立即暂停扩大范围或回滚；
- 观察结论：通过、延长观察、回滚、转缺陷/需求变更；
- 逃逸缺陷必须回到《执行反馈闭环标准》：补回归集、更新风险、必要时更新域标准/通用标准。

## 8. 效率与质量指标

每轮至少记录以下指标，按需求/月度复盘，不为指标而扩大用例：

| 指标 | 定义 | 数据源 |
| --- | --- | --- |
| 首版周期 | 需求接收→首版用例/策略卡 | 接收卡、版本记录 |
| 返工率 | 门禁修复条数/初版条数 | 门禁与修复记录 |
| 风险覆盖效率 | 已关闭高风险项/测试工时 | 风险矩阵、Execution ID |
| 执行覆盖率 | 实际执行条数/计划条数 | 执行账本 |
| BLOCKED率 | BLOCKED/计划执行条数 | 执行账本 |
| 证据检索时间 | 随机 TC 找齐证据链耗时 | 抽查记录 |
| 缺陷逃逸率 | 上线后发现缺陷/总缺陷 | 缺陷平台、观察台账 |
| 通道效率 | UI/API/脚本各自耗时与成功率 | 执行账本、netlog |
| 复用率 | 被变更集/多需求复用的用例占比 | 总库血缘 |

**采集器**：`usecase-executor/scripts/metrics_summary.py`——读执行账本 jsonl 自动汇总（兼容 执行记录/*_结果、pw_layered/ledger、dk_ui_results 三种字段形态），**禁手写**；执行收尾（usecase-executor 阶段三）必跑，结果进报告工件索引。缺陷逃逸率/首版周期/返工率不在账本范围，由报告阶段登记出处。

## 9. 追踪字段（与用例正文分离）

治理载体统一使用：

`risk_id`｜`risk_owner`｜`impact`｜`likelihood`｜`exposure`｜`case_priority`｜`test_depth`｜`nfr_dimension`｜`execution_set`｜`release_criterion_id`｜`execution_id`｜`evidence`｜`defect_or_change`｜`residual_risk`｜`risk_acceptor`｜`observation_metric`｜`observation_result`

这些字段进入策略卡、风险矩阵、Excel需求映射/统计说明和测试报告；用例正文仍保持五列表和设计/执行分离。

## 10. 过渡规则与休眠层（2026-11-11 立）

1. **存量八册豁免**：2026-11-11 前立项的八册（对客报价/仓内作业价格/配送价格/平台价格/通用计费/客户特定/云仓账单/存储账单）不追溯补策略卡、不批量改 P 级；其执行与报告沿用三层口径。
2. **历史三层口径标记**：跨册统计或横向对比 P0~P2 数据时，须注明"历史册为三层口径（其 P2 含新口径下属于 P3 的内容）"；历史册重出或用户明确要求复核时才迁移 P0123，并记录原级→新级理由与影响面（通用§1.1 迁移边界）。
3. **休眠层**：§6.3 发布 Go/No-Go 与 §7 上线后观察在当前内部测试环境无执行主体（无生产/灰度权限）——标记**休眠**，触发条件=获得生产或灰度环境权限；休眠期间策略卡相关字段可留空，不视为缺项。
4. **NFR 分流最小落地**：无工具支撑的维度（性能/兼容/可访问性）策略卡写"不测+理由+后续触发"即可，不强求空转填表；触发后按 §5 最小证据执行。
5. **P0123+策略卡首战**：挂账 00 索引（挂账⑤）；触发=下一新需求开工或存量册重出版本，首战用于校准四级判据与治理卡字段集。
