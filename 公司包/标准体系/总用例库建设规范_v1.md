# 总用例库建设规范 v1.0

> **目的**：定义"总用例库"的入库门槛、分层结构、生命周期与度量口径——把用例从"散落的文档"变成"可执行、可追溯、可度量的组织资产中枢"，并为平台化（PM 中心原生模块）提供数据模型。
> **适用范围**：全部测试用例资产（UI 用例、接口用例）、执行记录、缺陷关联与拍板记录。
> **现状底座**：需求用例库目录结构、历史版本归档纪律（usecase-history-cleanup 已自动化）、执行反馈闭环标准（L6）、接口用例血缘（接口标准 §7.2.7）均已落地——本规范将其收口为总库规则。

---

## 0. 三条总原则

1. **入库即资产**：只有过了门禁、拿到证书的用例才进现行库——未审 AI 产出、草稿、过程件一律不进。
2. **唯一正本**：每个需求每个版本只有一份现行正本（MD 源本），其余视图（XMind/Excel）从正本生成，差异=0 才交付。
3. **一切可追溯**：用例↔需求↔拍板↔缺陷↔执行记录五向可查——任何一条用例的"为什么这么写、执行结果如何、关联什么缺陷"都能在 3 分钟内查到。
4. **治理字段与正文分离**：风险、NFR、发布标准和上线观察不塞进五列表正文，统一挂在策略卡/风险矩阵/报告/总库索引。
5. **P0123现行、历史兼容**：新册按 `case_priority=P0/P1/P2/P3` 入库；历史三层册原样保留，重出或明确复核时才迁移并记录原级别→新级别。

## 1. 五条库规

### 库规一：入库门槛

| 入库动作 | 门槛 |
|---|---|
| AI 生成用例 | 两员门禁（生成方自查+质疑方独立复核）通过 + 九项尺子完成证书 |
| 人工编写用例 | 走 L5 门禁同级检查（结构/断言/数据三查） |
| 执行反馈修订 | 须经拍板（分流三选一）后修码重出，禁止执行侧直改 |
| 接口用例（UI 沉淀） | 按《接口测试用例编写标准》§7.2.5 基准确认 + §7.2.6 回放验证通过 |

### 库规二：分层结构

```
总用例库/
├── 需求文档/               # 需求原文+理解说明+拍板记录（财务线已有 1035+ 份）
├── 用例文件/
│   ├── {需求名}_标准测试用例.xlsx / .md      # 现行正本（唯一）
│   ├── {需求名}_分章/                        # 分章源（组装源，勿动）
│   └── 历史版本/                             # 旧版/草稿自动归档（含台账）
├── 接口用例/               # UI 沉淀+文档生成的接口用例（v1.1 格式，含血缘）
├── 执行记录/               # 每轮执行 results+报告（Execution ID 留痕）
└── 标准体系/               # L0~L7 分层标准（正本）
```

命名沿用现行《交付物规范》§18；归档动作由 usecase-history-cleanup 自动执行。

### 库规三：生命周期状态机

```
草稿 →（门禁+证书）→ 现行 →（需求变更/系统改版）→ 待复审 →（拍板修订）→ 现行
                                  ↘（需求下线/功能移除）→ 失效（划线+〔已失效〕+替代指针）
```

- **失效标识规范**：正文不动，标题加删除线+〔已失效〕+指向替代用例（L6 §13.3 既定纪律，2026-11-07 违规事故立的规）；
- **UI 用例改版联动**：UI 用例断言步骤删除/改版 → 血缘关联的接口用例自动标"待复审"（接口标准 §7.2.7）；
- **口径拍板联动**：断言基线库（BL 条目）变更 → 关联用例批量标"待复审"并留痕。

### 库规四：UI/接口双视图与血缘

- 同一业务资产两个视图：UI 用例（人读、界面执行）与接口用例（机器执行、回归主力），**不是两套资产**；
- 接口用例必带血缘字段：`{源UI用例编号, 源步骤号, 菜单, 租户, 采集时间, 采集执行ID}`；
- 断言基准以断言基线库/拍板记录为唯一正源（首录值≠正确值纪律）。

### 库规五：执行数据资产化

- 每轮执行全量落库：用例×结果×耗时×失败归因×流量（netlog）；
- 执行数据治理字段同步保留：`risk_id`、`case_priority`、`test_depth`、`nfr_dimension`、`execution_set`、`release_criterion_id`、`observation_metric`、`residual_risk`；
- 执行数据三个用途：①回归集变更选择的燃料（3~6 个月后解锁预测性选择）②质量度量看板（§2）③缺陷根因分析的对照组；
- 平台化承载：PM 中心原生模块 4 接口中的"回传结果（幂等）"即执行数据入口——总库就是这个模块的核心数据模型。

## 2. 度量口径（库的健康度）

| 指标 | 定义 | 目标 |
|---|---|---|
| 风险覆盖率 | 有证据关闭的高风险项 / 高风险项总数 | 100% 或逐条有风险接受 |
| 用例自动化率 | 可自动化用例 / 全量（按 P0 单列） | P0 ≥ 80%（对齐 L5 §19） |
| 接口沉淀率 | 已沉淀接口用例的 UI 用例 / 有接口交互的 UI 用例 | 首跑后 100% |
| 失效比 | 失效+待复审 / 现行 | < 5%（超过=批量复审信号） |
| 复用率 | 被变更集/多需求引用的用例占比 | 持续上升 |
| 拍板覆盖率 | 有对应拍板记录的歧义口径 / 已知歧义总数 | 100%（零未拍） |

## 3. 落地路径（不推倒、只收口）

1. **第一步（本周）**：按库规二结构盘点现有资产——现行正本/历史归档/执行记录归位（归档技能已自动化，预计半天）；
2. **第二步**：入库门槛接入生成流水线（门禁证书已有，补"无证书不得入库"的硬闸）；
3. **第三步**：执行记录统一入 `执行记录/`（本轮起执行产物按 Execution ID 归档）；
4. **第四步（随平台）**：PM 中心模块上线后，库从文件形态平移为平台数据模型——**文件即平台的导出视图**，双向同步。
