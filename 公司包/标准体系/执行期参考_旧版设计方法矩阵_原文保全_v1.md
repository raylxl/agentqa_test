## 6. AI 生成用例：设计方法与生成流程

AI 生成用例不采用"一个正向加几个反向"的固定套路，而是**先解析需求 → 按需求特征选用经典设计方法 → 按方法产出规则生成 → 覆盖自检**的四步流程，确保每个功能点用了什么方法、覆盖了什么，都有据可查。

### 6.1 生成流程（四步）

1. **需求解析**：AI 从 PRD/需求条目提取《需求要素清单》，固定结构输出：
   - 功能点列表
   - 输入字段及约束（类型 / 长度 / 必填 / 枚举取值 / 数值范围 / 默认值）
   - 业务规则（"条件 → 结果"的 if-then 形式）
   - 业务流程与状态流转（流程节点、分支、状态机）
   - 角色与权限
   解析结果随用例草稿一起输出，供审核人核对需求无遗漏、无理解偏差。
2. **方法匹配**：按 6.2 的矩阵为每个功能点选择设计方法，可多选叠加。
3. **用例生成**：按所选方法的产出规则（6.2 第三列）和本标准格式逐条生成。
4. **覆盖自检**：AI 随附《覆盖自检表》（6.4），列明每个功能点用了哪些方法、覆盖了哪些等价类 / 边界 / 规则列 / 迁移路径。

### 6.2 需求要素 → 设计方法选择矩阵

| 需求要素特征 | 选用方法 | 用例产出规则 |
|---|---|---|
| 有输入字段/表单（文本、数字、日期、文件） | 等价类划分 + 边界值分析 | 有效等价类尽量合并在正向用例中；**每个无效等价类单独一条**；数值型必测上/下边界及边界±1；长度型必测 0、最大、最大+1；枚举型每个取值至少出现一次 |
| 多条件组合决定结果的业务规则 | 判定表法（条件间有约束时先用因果图梳理） | 列全条件桩与动作桩生成判定表，**每条规则列至少 1 条用例**；组合数 >20 时先精简无关条件，仍过多转正交法 |
| 端到端业务流程（创建→审核→揽收→签收…） | 场景法 | 基本流 1 条；每个备选流（取消、驳回、超时、中断恢复）至少 1 条 |
| 单据/运单状态流转 | 状态迁移法 | 每个合法迁移 1 条；每个典型非法迁移（如已作废单据再编辑）1 条 |
| 多参数组合查询/筛选/配置项 | 正交实验法（成对组合 pairwise） | 全组合爆炸时按两两组合生成，并说明正交表选用依据 |
| 历史缺陷高发/易错点 | 错误推测法 | 平台将 PM 缺陷列表中该模块历史缺陷喂给 AI，针对性补强用例 |
| 多角色权限 | 角色-功能矩阵 | 每个角色"有权操作成功 / 无权被拦截"各 1 条 |
| 并发/时序类（库存扣减、重复提交、幂等） | 并发场景设计 | 标记"部分自动化"，或下沉到接口层执行 |

### 6.3 数量与优先级控制（防用例爆炸）

- 单个功能点 UI 用例常见区间 **5~15 条**；超出时 AI 必须说明原因，或建议将枚举穷举、罕见组合**下沉到接口层**（衔接"UI 执行沉淀接口用例"的分层策略）。
- 优先级映射：P0 = 场景法基本流 + 判定表主规则 + 主边界；P1 = 备选流 + 其余边界 + 权限；P2 = 罕见组合与错误推测补充。

### 6.4 覆盖自检表（AI 必须随用例草稿输出）

| 功能点 | 选用方法 | 覆盖项（等价类/边界值/规则列/迁移路径） | 用例编号 |
|---|---|---|---|

审核人按此表核对三件事：字段有没有漏做等价类、判定表规则列全不全、备选流和非法状态迁移有没有遗漏。

### 6.5 附加要求

1. **来源标记**：AI 从需求文档生成的用例标记 `AI生成-待审核`，人工审核通过后才进入执行池，审核动作记录留痕。
2. **同标合规**：AI 生成用例与人工用例执行同一套标准（动词表、断言表、变量规范），不符合即视为生成失败自动重生成，不带病入库。
3. **审核检查清单**（人工审核时逐项确认）：
   - [ ] 需求要素清单无遗漏、无理解偏差（功能点/字段/规则/流程/角色）
   - [ ] 方法选择合理，覆盖自检表与实际用例一致
   - [ ] 步骤在鲸天页面上真实可操作（菜单/按钮确实存在）
   - [ ] 预期与需求描述一致，且可判定
   - [ ] 测试数据可构造、可清理，粒度合规（一用例一验证点）
