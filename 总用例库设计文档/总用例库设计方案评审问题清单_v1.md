## 3. 问题明细

## R-01 一期生效点与 V2.5 主方案冲突

**等级：** P0  
**问题分类：** 分期边界 / 状态机 / 生效模型

### 现象

V2.5 主方案的 P1 阶段要求包含：

- `STAGED` 待发布状态；
- 上线事件触发合并；
- 临时号到正式号重映射；
- 上线前迭代回归；
- 上线后变更级回归。

见 V2.5 主方案 §16 分期计划。

但一期实施方案明确采用另一套模型：

- 变更单状态只有 `DRAFT / REVIEW / MERGED / REJECTED`；
- “待发布”不作为一期独立状态；
- 一期以“人工审批通过 + Git 合并提交”作为生效点；
- 审批通过后直接原子合并总库。

见一期方案 §3.2、§3.3、§4。

### 为什么是问题

这不是简单的功能裁剪，而是对以下核心语义给出了两种答案：

1. 用例什么时候正式生效；
2. `case_id` 什么时候分配；
3. 主库基线什么时候变化；
4. 回归快照基于什么状态生成；
5. 二期接入 `STAGED` 时是否需要历史数据迁移；
6. “一次审批”的审批对象是待合并内容，还是待上线内容。

如果团队按一期实施方案开发，二期再切换到 V2.5 主方案，会产生状态迁移和语义返工。

### 影响

- 开发会实现两套不同状态机；
- 试点数据可能需要补上线事件和生效时间；
- 回归快照的基线口径不一致；
- Agent 技能接口会随一期到二期发生变化；
- 管理层看到的“一期完成”与 V2.5 的 P1 完成定义不一致。

### 建议修正

必须先拍板一种模式：

**方案 A：严格按 V2.5 主方案执行**

- 一期即实现 `STAGED + 上线事件 + 合并`；
- 人工登记上线事件作为一期兜底；
- 一期方案删除“审批即合并”的表述；
- P1 验收包含上线前迭代回归和上线后变更级回归。

**方案 B：一期采用极简试点模式**

- 明确一期只是试点模式，不是 V2.5 P1 的完整实现；
- 定义一期 `MERGED` 与二期 `MERGED` 的语义差异；
- 给出一期数据升级到 `STAGED + release event` 模型的迁移方案；
- 明确二期切换前是否允许一期数据进入公司级推广。

不建议两份文档同时保留当前表述。

### 待拍板项

1. 一期是否必须实现上线事件生效模型？
2. 如果一期审批即合并，二期切换的迁移责任归谁？
3. V2.5 主方案和一期方案谁是一期范围准绳？

## R-02 跨系统“单一事务”不成立

**等级：** P0  
**问题分类：** 事务模型 / 数据一致性 / 合并实现

### 现象

V2.5 主方案 §13.1 要求上线合并必须在“单一事务”内完成：

1. 校验审批 hash 和上线事件；
2. 分配正式 `case_id`；
3. 临时号重映射；
4. 主库落库；
5. 清理待复审标记；
6. 重建索引并生成快照和 tag；
7. 封存临时号。

其中第 6 步包含 Git、SQLite、快照文件和 tag 多种存储对象。

一期方案 §13.1 的实际执行顺序是：

1. 生成完整目标状态；
2. 写入 Git 工作树；
3. 创建 Git commit；
4. 从 commit 重建 SQLite；
5. 生成回归快照。

并规定索引重建失败时不修改 Git 正本、保留上一版可用索引。但按该顺序，Git commit 已经创建后，索引才重建，实际无法保证“任一步失败整体回滚”。

### 为什么是问题

Git commit、SQLite 索引、快照文件和 tag 不是同一个事务资源。尤其 Git commit 创建后，如果 SQLite 重建失败，系统会进入：

```text
Git 正本已更新
SQLite 索引仍旧
快照缺失
tag 缺失
```

这不是原子事务，而是派生物滞后或构建失败。

### 影响

- 实现团队会误以为必须寻求不现实的跨系统回滚；
- 线上可能出现 Git 与索引不一致但系统未正确暴露的情况；
- 合并后快照和 tag 缺失时，无法判断主库是否可用；
- 故障恢复责任不清晰；
- 一期验收中的“索引可重建”不能等价于“合并原子性”。

### 建议修正

将事务模型改写为分层语义：

1. **合并前事务：** 在临时目录或 staged state 中完成编号分配、重映射、Schema 校验、目标状态生成；
2. **提交点：** Git commit 是唯一生效提交点；
3. **提交后派生物：** SQLite、快照、tag 均为可重建派生物；
4. **最终一致：** 派生物构建失败不回滚 Git，但合并记录必须标记为 `DERIVATIVE_BUILD_FAILED`；
5. **自动补偿：** 后台任务持续重建索引、快照和 tag，成功后标记恢复；
6. **可用性门禁：** 派生物未恢复前，禁止基于该 commit 生成新的回归执行；
7. **审计：** 记录 commit hash、索引构建版本、快照版本、tag 版本和恢复时间。

建议将“单一事务”改为：

> 合并前校验和目标状态生成必须原子完成；Git commit 是生效边界；索引、快照和 tag 是可重建派生物，通过补偿机制保持最终一致。

### 待拍板项

1. Git commit 后派生物失败时，是否允许主库保持已生效状态？
2. 派生物构建失败时，是否阻塞下一次变更合并？
3. 快照和 tag 是否允许后补？后补时如何证明与原 commit 对应？

## R-03 影响分析缺少稳定功能锚点

**等级：** P1  
**问题分类：** 数据模型 / 检索 / 影响分析

### 现象

V2.5 主方案 §8.1 的检索通道包含：

- 业务线；
- 系统；
- 域；
- 模块；
- 功能点；
- 租户；
- 客户版本；
- 状态。

但 §6.1 `test_case` 字段中没有稳定的 `system_id / domain_id / module_id / function_point_id` 等结构化锚点字段。现有字段主要包括：

- `title`；
- `preconditions`；
- `steps`；
- `expected_results`；
- `basis_refs`；
- `source_requirement_ids`；
- `legacy_ids`。

仓库结构虽然有业务线、域、模块目录，但目录路径不是稳定业务身份。

### 为什么是问题

总用例库的核心价值是复用和影响分析。如果缺少稳定功能锚点，影响分析会主要依赖：

1. 标题和正文文本；
2. 需求引用；
3. 历史编号；
4. 目录路径；
5. 语义召回。

这些都会在业务改名、菜单迁移、模块重组、需求描述差异、同义词缺失时失效。

### 影响

- 新需求漏召回历史用例；
- 重复新增同类用例；
- AI 对 `UNAFFECTED / MODIFY / RETIRE` 的判断依据不稳定；
- 多业务线之间难以复用；
- 二期 MR 代码路径映射缺少承接点；
- 存量迁移判重依赖文本相似度，误判率偏高。

### 建议修正

新增独立的功能锚点模型，例如：

```text
function_anchor
├── anchor_id
├── business_line_id
├── system_id
├── domain_id
├── module_id
├── function_point_id
├── canonical_name
├── aliases
├── menu_path
├── route / api_refs
├── status
└── version_history
```

用例增加：

```text
primary_anchor_id
related_anchor_ids
```

并规定：

1. `primary_anchor_id` 是影响分析的强过滤条件；
2. 文本和语义检索只作为补充召回；
3. 锚点改名不影响 `anchor_id`；
4. 菜单迁移通过锚点关系保留血缘；
5. MR 映射到锚点，而不是直接映射到用例标题。

### 待拍板项

1. 功能锚点的唯一来源是菜单、接口、页面路由，还是独立业务目录？
2. 锚点主数据由谁维护？
3. 存量迁移时是否允许临时锚点？如何治理？
4. 锚点缺失的用例是否允许进入 ACTIVE？

## R-04 适用范围口径前后不一致

**等级：** P1  
**问题分类：** 数据模型 / 全量回归 / 分期边界

### 现象

V2.5 主方案 §6.2 规定：

- P0/P1 只强制 `business_lines` 与 `product_version_from`；
- `tenant_scope` 与 `customer_scope` 可标记 `PENDING_SCOPE`；
- P2 结束前补齐；
- `PENDING_SCOPE` 用例不进入全量回归执行分母；
- 不得默认 `ALL`。

但一期方案出现另一套口径：

1. 一期范围包含业务线、租户、客户版本适用范围；
2. 用例示例直接使用 `tenant_scope: ALL`、`customer_scope: STANDARD`；
3. 全量回归按业务线、租户、客户版本、产品版本四轴过滤；
4. 存量迁移要求补齐业务线、租户、客户、版本；
5. 一期验收要求试点业务线适用范围完整率 100%。

### 为什么是问题

同一套“一期”存在两种适用范围要求：

```text
主方案：两轴必填 + 两轴 PENDING_SCOPE 过渡
一期方案：四轴有效并参与全量过滤
```

这会直接改变全量回归分母、治理任务量、迁移门槛和一期验收标准。

### 影响

- 一期开发无法判断 Schema 是否允许 `PENDING_SCOPE`；
- 全量纳入率分母不一致；
- 存量迁移工作量被低估或高估；
- 二期治理单数量不可预测；
- 验收结论不可比较。

### 建议修正

统一为一套过渡规则，建议采用：

1. 新增用例：试点期也必须四轴明确，禁止新增 `PENDING_SCOPE`；
2. 存量迁移：允许 `PENDING_SCOPE`，但只能来自历史数据；
3. 全量回归：`PENDING_SCOPE` 不进入执行分母，必须进入待补清单；
4. 一期验收：适用范围完整率拆成两个指标：
   - 新增用例四轴完整率 100%；
   - 存量迁移用例四轴完整率单独统计，不伪装成 100%。
5. P2 结束前完成存量 `PENDING_SCOPE` 清零。

### 待拍板项

1. 新增用例是否允许 `PENDING_SCOPE`？
2. 一期试点验收是否要求存量四轴完整率 100%？
3. `PENDING_SCOPE` 的最长允许存续时间？
4. 谁负责补齐：业务测试、测试负责人，还是治理任务自动分派？

## R-05 治理型变更低估了适用范围变更的执行影响

**等级：** P1  
**问题分类：** 治理变更 / 回归策略 / 风险控制

### 现象

V2.5 主方案 §13.3 规定治理型变更用于补齐适用范围等纯治理字段：

- 更新 `case_applicability`；
- 递增 `case_version`；
- 重建索引；
- 不生成回归快照；
- 理由是“治理变更不改用例执行内容”。

### 为什么是问题

适用范围本身就是执行准入条件。将用例从 `PENDING_SCOPE` 补成明确的租户或客户范围，会改变该用例的执行域：

```text
原状态：不进入全量回归分母
补齐后：进入对应租户/客户的全量回归范围
```

因此“不改步骤和预期”不等于“不影响执行范围”。

### 影响

- 新纳入范围的用例可能从未在目标租户或客户环境验证；
- 范围补齐错误要等到下次发版或月度全量才发现；
- 治理合并缺少执行证据；
- 后续缺陷难以判断是范围补错还是用例本身失效。

### 建议修正

治理型变更分两类处理：

**A 类：无执行语义变更**

- 仅修正编号、名称、描述、归档元数据；
- 可不生成回归快照。

**B 类：适用范围变更**

- 必须生成 `governance_scoped` 快照或最小验证清单；
- 至少执行目标范围内冒烟验证；
- 记录范围变更前后差异；
- 若范围扩大，验证新纳入目标；
- 若范围缩小，记录排除依据；
- 执行结果写入治理变更审批包。

### 待拍板项

1. 适用范围补齐是否必须执行验证？
2. 最小验证集由谁定义？
3. 无法自动化时是否允许人工确认？
4. 范围补齐后多长时间内必须完成验证？

## R-06 上线事件与变更单关系建模不清晰

**等级：** P1  
**问题分类：** 发布建模 / 状态机 / 平台接口

### 现象

V2.5 主方案中 `case_change_set` 包含单个：

```text
release_event_id
target_release_version
```

二期方案中上线事件又包含单个：

```text
change_set_id
```

这隐含一对一关系，但发布现实通常是：

1. 一次发布包含多个变更单；
2. 一个变更单可能进入多个环境；
3. 灰度发布可能分批生效；
4. 热修和回滚会改变上线状态；
5. 发布回调可能重复、乱序或延迟。

### 为什么是问题

如果上线事件和变更单是一对一，会导致：

- 同一次发布要复制多条上线事件；
- 发布状态变化无法统一维护；
- 多批次发布难以追踪；
- 回滚无法表达；
- 事件幂等和乱序处理没有承载体。

### 影响

- `STAGED` 长期滞留或误合并；
- 同一发布批次内冲突预检不稳定；
- 发布平台接入成本升高；
- 合并审计无法还原真实发布链路。

### 建议修正

将关系改为三实体模型：

```text
release_event
├── release_event_id
├── release_batch_id
├── target_release_version
├── environment
├── rollout_status
├── released_at
├── source
└── idempotency_key

release_change_set
├── release_event_id
├── change_set_id
├── association_status
├── merged_commit
└── linked_by

case_change_set
└── 不直接保存唯一 release_event_id
```

同时定义：

1. 一个发布事件关联多个变更单；
2. 一个变更单在不同环境的事件通过发布批次关联；
3. 回滚不删除事件，只追加状态；
4. 重复回调通过 `idempotency_key` 去重；
5. 乱序事件先入队，不直接触发合并；
6. 只有明确的有效上线事件才触发合并。

### 待拍板项

1. 一次灰度发布是一个 release event，还是每个灰度批次一个 event？
2. 回滚后已合并用例如何表达？是否走新的失效变更单？
3. 发布平台是否保证提供发布批次 ID？
4. 人工登记上线事件的审批和追责规则是什么？

## R-07 全量回归缺少容量模型，指标可能失真

**等级：** P1  
**问题分类：** 回归策略 / 验收指标 / 运营成本

### 现象

V2.5 主方案规定：

- 全量回归按发版或月度触发；
- P0/P1/P2/P3 全部进入；
- 优先级只决定执行顺序；
- `manual_only` 用例也进入快照；
- 无法执行时记录 `BLOCKED` 或 `NOT_EXECUTED`；
- 不得从分母删除。

### 为什么是问题

该规则保证了口径严格，但缺少容量约束。公司级规模下可能出现：

```text
快照纳入率 100%
实际执行完成率很低
大量 NOT_EXECUTED / BLOCKED
全量回归时长超过窗口
```

如果验收只看纳入率，会产生“绿色但不真实”的结果。

### 影响

- 全量回归无法按期完成；
- 人工用例长期积压；
- 自动化率不足的问题被纳入率掩盖；
- 发版决策缺少真实执行覆盖信息；
- 测试团队对“全量”产生抵触。

### 建议修正

将指标拆分为：

| 指标 | 含义 |
|---|---|
| 快照纳入率 | 应纳入用例是否都进入快照 |
| 实际执行完成率 | 快照内实际执行完成的占比 |
| 自动化执行率 | 可自动执行且已自动执行的占比 |
| 人工执行完成率 | `manual_only` 中实际完成的占比 |
| 阻塞率 | `BLOCKED` 占比及原因分布 |
| 未执行率 | `NOT_EXECUTED` 占比及原因分布 |
| 时长达成率 | 是否在规定执行窗口内完成 |

并要求：

1. 每轮全量回归前生成容量预估；
2. 超出窗口时不得静默裁剪，必须输出执行策略决策；
3. 若采用分批执行，快照仍全量，执行计划分批；
4. 全量回归报告必须同时展示纳入率和执行完成率；
5. `manual_only` 单独统计，不与自动化用例混算。

### 待拍板项

1. 全量回归最大允许执行窗口；
2. 超窗时允许暂停、分批，还是升级决策；
3. `manual_only` 是否设置最低抽检比例；
4. `NOT_EXECUTED` 连续多少轮后自动触发治理。

## R-08 多份方案文档出现多正本漂移

**等级：** P2  
**问题分类：** 文档治理 / 配置管理

### 现象

当前 4 份文档分别维护状态机、分期计划、接口和验收指标，已经出现不一致：

1. V2.5 主方案一期包含 `STAGED` 和上线事件；
2. 一期方案审批即合并，不设 `STAGED`；
3. 二期状态机使用 `REVIEW_PENDING`；
4. 二期 Web 页面仍写 `DRAFT/REVIEW/STAGED`；
5. V2.5 与一期方案对适用范围要求不同。

### 为什么是问题

多正本手工维护会导致后续每次修订都可能产生新分歧。开发、测试、管理层分别阅读不同文档时，会得出不同的实施结论。

### 影响

- 需求评审反复争论口径；
- 开发实现依据不唯一；
- 汇报版与落地方案脱节；
- 后续修订成本持续增加。

### 建议修正

1. 指定 `总用例库建设方案-g-V2.5.md` 为唯一规范源；
2. 一期、二期、汇报精简版标记为派生文档；
3. 派生文档只保留摘要，不重复定义状态机和数据模型；
4. 修订时先改主方案，再同步派生文档；
5. 建立文档同步检查清单；
6. 所有状态名、分期名、接口名从主方案复制，不允许派生文档自行缩写。

### 待拍板项

1. 哪份文档是唯一规范源？
2. 汇报精简版是否允许保留完整状态图？
3. 文档同步责任人是谁？

## 5. 复审验收标准

设计问题闭环后，应满足以下标准：

1. 一期、二期、主方案对“生效点”的表述完全一致；
2. 合并事务模型可实现，并明确失败恢复路径；
3. 用例存在稳定功能锚点，影响分析不依赖目录路径和标题文本；
4. 适用范围的必填、过渡、分母和验收口径唯一；
5. 治理范围变更具备验证或明确的风险接受记录；
6. 上线事件支持一次发布多个变更单、多环境、重复回调、乱序和回滚；
7. 全量回归同时报告纳入率和实际执行完成率；
8. 所有派生文档与唯一规范源一致。
